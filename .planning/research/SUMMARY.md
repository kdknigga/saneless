# Project Research Summary

**Project:** saneless
**Milestone:** v2.0 "Prep for release" — hardening driven by `.planning/reviews/2026-09-09-code-review.md` (10 CRITICAL, 34 MAJOR, 45 MINOR/NIT, 10 USABILITY findings)
**Domain:** Self-hosted SANE-scanner → paperless-ngx bridge appliance (Python 3.14, FastAPI+HTMX, Click, SQLite, threaded worker)
**Researched:** 2026-09-09
**Confidence:** HIGH

## Executive Summary

This is not greenfield research — it is a hardening pass on a working, well-structured appliance. All four researchers agree with the review's own verdict: "the codebase is not under-engineered; it is under-connected." The stack needs zero new runtime dependencies — every capability the review demands (thread-safe SQLite, sync FastAPI routes, bounded queue with 429, strict `extra="forbid"` config, atomic TOML writes, correct PDF DPI, page spooling, vendored front-end assets, `Sec-Fetch-Site` CSRF protection, hermetic tests, `saneless doctor`, truthful SANE fakes) is satisfiable with the standard library and packages already pinned; the dependency work is subtraction and version hygiene, not addition. On the feature side, the milestone's user-facing payoff is an "appliance layer" (`U-01`..`U-10`): a shared status-strip/`doctor` diagnostic pair, honest per-job outcomes (page counts, a `FALLBACK` state, plain-language errors), working manual duplex, and "never lose a scan" defaults — all things the closest competitor (scanservjs) conspicuously lacks and the wider self-hosted admin-tool class (paperless-ngx, Nextcloud, Home Assistant) treats as table stakes.

The recommended approach is architectural, not additive: introduce two small leaf modules (`states.py` for the vocabulary every renderer must agree on, `results.py` for the typed pipeline outcome) so that "one enum, one label map, one classifier" becomes something the type checkers (`ty`, `pyrefly`, both already CI gates) can enforce rather than a convention that keeps drifting back into three copies. The single most important discipline the roadmap must impose is ordering: the review's own section-10 remediation order is broadly sound, but both the ARCHITECTURE and PITFALLS researchers independently found the same handful of places where following it literally reintroduces a bug the review is trying to fix (the clearest example: fixing the atomic config write, `M-10`, before fixing the bind-mounted-file compose deployment, `M-30`, makes `os.replace` fail with `EBUSY` on the exact deployment the docs recommend). This document's "Implications for Roadmap" section gives one reconciled phase spine that resolves every such conflict found.

The dominant risk category is not "will this work" but "will a mechanically-correct fix for one finding quietly break an adjacent one that isn't in the same review bullet." Nine of PITFALLS.md's 22 numbered pitfalls are exactly this shape (e.g., adding `JobState.FALLBACK` before consolidating the label maps renders a blank status area; making `poll_task` raise on `FAILURE` deletes the PDF unless the preservation code is widened to cover the poll call, not just the upload call). Mitigation is procedural: every phase in the reconciled spine below is scoped so its own tests would have failed before the phase and cannot silently regress after — the "green-suite checkpoint" discipline both ARCHITECTURE.md and PITFALLS.md converge on independently.

## Key Findings

### Recommended Stack

Zero new runtime dependencies. The work is: drop the `pydantic-settings[toml]` extra (stdlib `tomllib` already covers it on Python ≥3.11), bump ~8 runtime/dev pins to current, vendor htmx 2.0.10 and PicoCSS 2.1.1 with pinned SHA-384 digests (`N-21` — offline LAN is the stated environment), pin 6 GitHub Actions to commit SHAs with Dependabot maintaining them (`M-26`, `N-31`), fix the PEP 639 license-classifier conflict that would make the first `git push --tags` fail at PyPI (`N-30`), and optionally add `zizmor` (workflow security audit) and `pytest-timeout` (CI hang guard) as dev-only tools.

**Core technologies (unchanged, validated in v1):** stdlib `sqlite3` + `threading.RLock` for the job store (not per-thread connections — `:memory:` databases used throughout the test suite would silently diverge); stdlib `queue.Queue` with `put_nowait`/`WorkerBusyError` for backpressure (not `rq`/`celery`/Redis — explicitly out of scope and unneeded at this scale); `img2pdf.get_fixed_dpi_layout_fun` for correct PDF geometry (root cause of `M-06`: `img2pdf.default_dpi == 96.0`); `Sec-Fetch-Site` header check for CSRF-equivalent protection without adding a session/auth layer the product deliberately doesn't have (`N-22`, `U-09`).

**What NOT to add:** `platformdirs` (Linux-only project — 5-line stdlib XDG helper suffices), `freezegun`/`time-machine` (both mishandle `time.monotonic()` in ways that would make the cache-TTL and flip-timeout tests either flaky or untestable — two `monkeypatch.setattr` calls do the whole job), `atomicwrites` (unmaintained; 9 lines of `tempfile`+`os.replace` suffices), `starlette-csrf`/session middleware (needs auth the product doesn't have), `rich` (would create a second CLI output style next to the existing hand-rolled tables), htmx 4.x (rewrite with different swap semantics — the `C-10` fix is written against htmx 2).

### Expected Features

The milestone's feature scope is the review's own section 11 (`U-01`..`U-10`) plus the user-visible half of the CRITICAL fixes. Peer research (paperless-ngx, Nextcloud, Home Assistant, Immich, scanservjs, NAPS2) makes the priority split evidence-based rather than asserted.

**Must have (table stakes — P1, ship in v2.0):**
- Status strip (Scanner/Paperless/Profiles/Fallback) + `saneless doctor` sharing one check registry (`U-03`) — every peer in the admin-tool class has an equivalent; saneless is currently below the floor
- Honest per-job outcome: page counts, `FALLBACK` state, warnings rendered distinctly (`U-02`, `C-03`)
- Plain-language errors with a next step, raw text behind `<details>` (`U-05`) — blocked on `M-11` landing first, or the friendly message is confidently wrong
- Human profile labels/descriptions generated at startup (`U-04`)
- Placeholder-token detection at startup (`U-01`) — refuse to *scan*, never refuse to *boot* (the status strip is the only diagnostic surface an appliance has)
- Consume-dir fallback + `failed/` mounted by default (`U-08`, needs `C-04`+`C-05` together)
- CLI flip prompt + flip timeout (`C-01`, `C-02`, `M-07`)
- Local-time timestamps (`M-23`), help text under form fields (`U-07` first half), trust-model + "which setup do I have" docs (`U-09`, `U-10`)

**Should have (differentiator — P2, v2.x once P1 is proven):** queue position visibility (`U-06`, needs `C-09`), owner-only flip prompt via browser token framed explicitly as a footgun guard and never as auth (`U-06`), checkbox tag picker + hide-fields option (`U-07` second half).

**Anti-features (explicitly rejected):** refusing to start on a placeholder token (kills the only diagnostic surface); a full first-run setup wizard (fights the read-only-config-mount and no-auth constraints); real user accounts to solve the shared-flip-prompt problem (out of scope, and would give false security confidence); a retry-upload button (needs a durable identified PDF store this milestone doesn't build); a JS combobox library (breaks the "no build step" decision for one control); reusing `/health` as the status-strip source (couples liveness to a slow Paperless call — the `M-01` failure mode again).

### Architecture Approach

Not a redesign — an integration plan for where each new piece attaches to the existing, sound module graph. Two new leaf modules carry the milestone's central discipline: `states.py` (the single `JobState` enum, `ACTIVE_STATES`, `STATE_LABELS`, `ERROR_MESSAGES` — what every *renderer* must agree on) and `results.py` (`ScanOutcome`, `ScanResult`, `UploadResult` — what the *pipeline* produces). Both are leaves that import nothing from `saneless`, which is what makes "one enum, one label map, one classifier" (`M-05`, `C-06`) mechanically enforceable by `ty`/`pyrefly` instead of a convention people re-violate.

**Major new/changed components:**
1. `delivery.py` (NEW) — owns the "never lose a scan" policy: upload → consume-dir fallback → preserve under `failed/`; the one place that can fix what today is split unfixably between `paperless.py` and `pipeline.py` (`C-03`, `C-04`, `C-05`)
2. `flip.py` (NEW) — a single required-when-manual `FlipCoordinator` Protocol replacing two independently-nullable events, so the CLI can no longer forget to supply one (`C-01`, `C-02`, `M-07`, the exact shape of the `C-02` bug)
3. `doctor.py` (NEW) — `Check` dataclasses shared by the CLI, the web status strip, and eventually docs; must accept a `busy: bool` and never import `worker.py`, because the scanner is exclusive hardware a diagnostic probe could contend with (`U-03`)
4. `job.py` (MODIFIED) — `RLock` + `PRAGMA user_version` migration ladder + new result columns, replacing a bare `except sqlite3.OperationalError: pass` that silently swallows real corruption (`C-07`)
5. `web/routes.py` / `web/templates/` — `async def` → `def` (routes become legally blocking, `M-01`), server-owned Scan button via `hx-swap-oob` replacing `app.js` (`C-10`)

**Key patterns:** (1) typed result flowing through four layers so nothing optional can be forgotten (`C-03`); (2) one required collaborator object instead of two optional events (`C-02`); (3) server-owned UI state via out-of-band swap (`C-10`); (4) spool-as-you-scan with content-ordered page records, not path globs (`M-08`); (5) diagnostics as data rendered three ways (`U-03`).

### Critical Pitfalls

1. **A correct `poll_task` raise deletes the PDF it was supposed to protect** (`C-03`+`C-04`+`M-22`) — if the preservation `try/except` only wraps `upload_document` and not the later `poll_task` call, a `FAILURE` response now correctly raises *and* the `TemporaryDirectory` unwinds and deletes the document. Write preservation as one `try/except` spanning both calls, and make the first test of this work "poll returns FAILURE → a PDF exists on disk and the error names its path."
2. **"Preserved" files land in a directory the OS or a container rebuild deletes** (`C-04`, `N-39`, `U-08`) — `tmp_dir` defaults to `/tmp/saneless` and isn't on any volume in the recommended compose. Introduce `output.data_dir` (XDG state) for `saneless.db` and `failed/` in the same phase that adds `failed/`, not a later config or delivery phase.
3. **`extra="forbid"` on nested models turns a stray env var in someone's `docker-compose.yml` into a boot-crashing typo, and the existing error renderer names the wrong section** (`M-18`) — `_build_settings` currently reads only `loc[0]`; nested forbid produces `loc == ("paperless", "tokne")`, and the naive renderer would confidently blame the wrong section. Rewrite the renderer to use the full `loc` path before enabling nested `extra="forbid"`.
4. **The atomic config write (`M-10`, `os.replace`) cannot succeed on the compose deployment the docs recommend** (`M-30`) — renaming over a bind-mounted *file* returns `EBUSY` on Linux; only mounting the *directory* makes atomic replace possible. These two findings are filed in different review areas and, done in review order, ship a "durable write" that is broken on day one for the documented setup.
5. **htmx 2's default `responseHandling` does not swap 4xx bodies**, so the `429`/`503` backpressure the C-09 fix introduces is invisible to the user — clicking Scan while the queue is full produces no visible change at all, reintroducing exactly the `C-10` symptom the milestone is separately fixing. Requires an explicit `htmx-config` `responseHandling` override (or a documented 200-with-error-body compromise for HTML routes only).
6. **The `JobStore` lock is necessary but not sufficient**: `RLock` is re-entrant, but `with self._conn` is not — a public method calling another locked public method silently splits one transaction into two. Public methods must call private, lock-free `_impl` helpers; no public-to-public calls.

## Implications for Roadmap

### Reconciling the two build-order proposals

Both the ARCHITECTURE and PITFALLS researchers independently concluded that the review's own section-10 order (11 steps, appliance layer last) is directionally right but unsafe to follow literally in five to seven places. **They largely converge on the same underlying dependency reasoning even though they express it differently** — ARCHITECTURE proposes a fully renumbered 13-step build order (steps 0–12); PITFALLS keeps the review's original step numbers as reference points and flags specific hazards where a later step invalidates an earlier one. Reading them together:

**Where they agree (both independently arrived at the same correction):**
- **CI must come first**, not at the review's original step 7. ARCHITECTURE makes this its step 0 explicitly. PITFALLS' entire framing ("each step leaves the suite green") depends on this being true from the start, and never contradicts moving it earlier.
- **The JobStore lock + a real `PRAGMA user_version` migration ladder must land before, or in the same step as, the first new result column** — not as another bare `ALTER TABLE ... except: pass`. ARCHITECTURE makes this its step 2 (ahead of the typed-result work that needs the columns). PITFALLS states the same requirement directly (Pitfall 16, and the Cross-Step Ordering Hazards table: "Job-table columns... No migration mechanism... Add `PRAGMA user_version` migrations... before the first new column").
- **`M-06` (PDF DPI) must move with `C-05` (unique PDF names)**, not stay at the review's original step 8 — both touch `assemble_pdf`'s signature and the same 85-line test module. ARCHITECTURE states this explicitly; PITFALLS' Pitfall 15 (spool ordering) assumes the same consolidated signature.
- **Durable storage (`output.data_dir`/`state_dir`) must be introduced in the same phase as `C-04`'s `failed/` preservation**, not deferred to a later config or delivery phase. Both explicit (ARCHITECTURE step 3; PITFALLS Pitfall 2 and the ordering-hazards table).
- **Worker-test sleep removal tied to the `stop()`-semantics change must happen when `C-09` changes those semantics, not in the later hygiene sweep.** PITFALLS is emphatic here (Pitfall 17: "This is a direct conflict between Step 4 and Step 9 and must be planned for") — deleting the 26 sleeps under the assumption that `stop()` still drains the queue, after `C-09` replaces the blocking sentinel with a stop-flag loop, produces a suite that is flaky in exactly the way the sleeps were hiding. ARCHITECTURE's step 6 (worker robustness) does not explicitly call this out and its own step 12 ("remove the 26 sleeps") reads as if it could be done in one late pass — **this is a real gap in ARCHITECTURE that PITFALLS catches**; the reconciled spine below follows PITFALLS and splits the sleep work.

**Where they differ (and my recommendation):**

| Point of difference | ARCHITECTURE's position | PITFALLS' position | Recommendation |
|---|---|---|---|
| Scanner truthfulness vs. manual duplex order | Explicitly flips the review's order: scanner layer (`C-06`, `M-11`, `M-14`, `M-32`) *before* manual duplex, because `M-14`'s backend white-page removal changes duplex page parity and `M-32`'s honest fakes are what make a duplex test meaningful | Doesn't explicitly reorder — frames `C-01` as living in the review's original "step 2" (duplex) and scanner findings in "step 3", i.e. duplex-then-scanner, matching the review's literal order. Its own content (Pitfall 15 on `M-14`'s interaction with spooling, Pitfall 17 on landing `M-32` "in the same phase as the backend fixes it exposes") is consistent with, but doesn't itself demand, the swap | **Follow ARCHITECTURE.** A duplex correctness test written against the current `MagicMock`-based fakes or against a backend that still silently drops white pages is testing a system that won't exist after the following phase — better to fix the ground truth first. This is a genuine improvement PITFALLS doesn't contradict. |
| Where `M-30` (mount the config directory, not the file) is scheduled | Not explicitly scheduled in the step-by-step table; "compose token/mount fixes" appears bundled into the *appliance layer* step (step 10), while `M-10`'s atomic write lands earlier in the *configuration strictness* step (step 7) — **this reproduces the exact hazard PITFALLS warns about** | Explicit and detailed: `M-10` and `M-30` must land in the *same* phase, because `os.replace` over a bind-mounted file returns `EBUSY` on the deployment the docs recommend (Pitfall 8, ordering-hazards table) | **Follow PITFALLS.** Pull `M-30` forward into the configuration-strictness phase, alongside `M-10`. This is the clearest case of ARCHITECTURE's plan silently recreating a bug PITFALLS independently found — treat it as a correction, not a stylistic preference. |
| Where htmx/PicoCSS vendoring (`N-21`) is scheduled | Not explicitly placed in the step table at all (STACK.md treats it as a standalone dependency task with no phase assignment) | Explicit: vendor at pinned versions in the *same* phase as the `C-10` browser regression test, because a CI sandbox has no egress and CDN-loaded assets make that test flaky or impossible (Pitfall 20, ordering-hazards table) | **Follow PITFALLS.** Fold `N-21` vendoring into the worker-and-web-robustness phase that adds the `C-10` browser test, not a later cleanup sweep. |

None of these are deep disagreements about the destination — both researchers want the same end state (the review's 99 findings resolved, in an order where every phase's own tests stay green forever after). The differences are about *which phase a shared piece of work belongs to*, and in every case one researcher's reasoning is more specific and directly falsifiable than the other's silence on the point, which is why the reconciliation above resolves cleanly rather than requiring a coin flip.
