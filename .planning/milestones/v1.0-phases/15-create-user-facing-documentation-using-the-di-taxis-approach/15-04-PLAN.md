**docs/explanation/architecture.md** (per D-09 item 1):
- Title: `# Architecture Overview`
- Opening: What saneless does at a high level -- bridges SANE scanners to paperless-ngx
- Section: **The Scan Pipeline** -- describe the flow:
  1. **Scanner abstraction** -- `ScannerBackend` ABC isolates SANE behind clean methods (`open()`, `scan()`, `multi_scan()`, `close()`). The `SaneBackend` implementation wraps `python-sane`. This means the core pipeline never touches SANE directly.
  2. **Pipeline orchestration** -- `run_pipeline()` coordinates the scan flow: detect scanner -> set parameters -> acquire pages -> filter empty pages -> assemble PDF -> upload to paperless. Each stage emits a `PipelineEvent` (SCANNING, ASSEMBLING, UPLOADING, DONE, ERROR).
  3. **PDF assembly** -- Uses `img2pdf` to convert scanned PIL images to PDF. Lossless -- no re-encoding of image data.
  4. **Paperless upload** -- `PaperlessClient` sends the PDF via multipart POST to paperless-ngx API with metadata (title, tags, correspondent). Falls back to consume directory if API is unavailable.

- Section: **Worker Thread Model** -- The web server runs a background worker thread that processes one scan job at a time. Jobs are queued and executed sequentially (scanning is inherently serial -- one scanner, one job). The worker communicates status back to the web layer via state transitions on the `Job` object, which the UI polls via HTMX.

- Section: **Configuration Layer** -- pydantic-settings with TOML file + environment variable override. Config search paths. Profile system for storing scanner presets.

- Section: **Web Layer** -- FastAPI with Jinja2 templates and HTMX for reactivity. No JavaScript framework. PicoCSS for styling. The web UI is a thin layer over the same pipeline the CLI uses.

**docs/explanation/empty-page-detection.md** (per D-09 item 2):
- Title: `# How Empty Page Detection Works`
- Problem: ADF duplex scanning often produces blank backs. Users don't want blank pages in their PDFs.
- Algorithm: For each scanned page, convert to grayscale and compute two statistics:
  1. **Mean luminance** -- average pixel brightness (0=black, 255=white). A blank white page has mean close to 255.
  2. **Standard deviation** -- how much pixel values vary. A blank page has very low stddev (nearly uniform).
- Detection rule: A page is considered empty if BOTH conditions are true:
  - `mean > empty_page_mean_threshold` (default: 250.0)
  - `stddev < empty_page_stddev_threshold` (default: 5.0)
- Why both thresholds: Mean alone would miss pages with a small mark on an otherwise white page. Stddev alone would miss uniformly gray pages. Together they reliably identify truly blank pages.
- Tuning: Lower the mean threshold or raise the stddev threshold to be more aggressive. Adjust in profile config:
  ```toml
  [profiles.duplex]
  empty_page_mean_threshold = 245.0
  empty_page_stddev_threshold = 8.0
  ```
- Disabling: Set `enable_empty_page_detection = false` in the profile to keep all pages.

**docs/explanation/consume-directory-fallback.md** (per D-09 item 3):
- Title: `# How Consume Directory Fallback Works`
- Problem: If paperless-ngx is temporarily unavailable (maintenance, network issue), scanned documents shouldn't be lost.
- Solution: When `paperless.consume_dir` is configured and the API upload fails, saneless deposits the PDF into the consume directory instead.
- How paperless-ngx picks it up: paperless-ngx has a "consumption" feature that watches a directory for new files and imports them automatically. By pointing saneless's consume_dir at paperless's consumption directory, documents are ingested when paperless comes back online.
- Limitations: Metadata (title, tags, correspondent) is NOT preserved in the consume directory fallback -- only the PDF file is saved. Paperless applies its default processing rules.
- Configuration:
  ```toml
  [paperless]
  url = "http://paperless.local:8000"
  token = "abc123def456"
  consume_dir = "/path/to/paperless/consume"
  ```
  In Docker, mount the consume directory as a shared volume between saneless and paperless containers.
- When it activates: Only when the API upload fails (connection refused, timeout, auth error). If no `consume_dir` is configured, the error propagates and the job enters ERROR state.
