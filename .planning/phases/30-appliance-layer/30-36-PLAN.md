<objective>
Turn the manual-refresh floor's last narrative invariant into an enforced one, and record what this
gap-closure round did and did not close.

Purpose: `release_manual_claim` clears with `self._last_manual_claim = None` and no check that the
stamp being cleared is the caller's own. The docstring's argument holds today -- the only caller
releases microseconds after its grant, on the same thread, and a competing claimer inside that
window is refused without writing -- but it is a narrative invariant about one call site, not an
enforced one, and none of the five `TestReleaseManualClaim` cases exercises two threads. A compare
-and-clear costs one parameter and removes the reasoning entirely, which is the right trade for a
floor whose whole job is to bound what an unauthenticated LAN endpoint can make the appliance do.

Output: `claim_manual_refresh` reports the stamp it wrote, `release_manual_claim` clears only that
stamp, the one caller carries it between the two, and a two-thread test says so.

## Out of scope

The floor's value, the bypass it sits under (D-09), the single-flight collapse and the
"did I probe" contract `probe_now` reports are all unchanged. This plan changes who may clear the
stamp, and nothing else about when a refresh is allowed.
</objective>

## Why compare-and-clear rather than a second lock or a token object

The stamp is already a float written under `self._lock`; returning it costs nothing and makes the
release's precondition checkable at the point of use. A dedicated token object would add a type for
a value that is a timestamp and is compared for equality. A second lock would add ordering rules to
a class whose whole appeal is that it has one.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated LAN client -> `POST /api/checks/refresh` | the endpoint is reachable without credentials by design and `CrossOriginGuard` admits a request carrying neither `Sec-Fetch-Site` nor `Origin`, which is what a scripted client sends |
| request thread -> `_last_manual_claim` | several request threads can be inside the cache at once; the floor is the only thing bounding how often an unauthenticated caller can make the appliance probe |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-36-01 | Denial of Service | `release_manual_claim` | mitigate | compare-and-clear, so no caller can clear a grant it did not make; the 2 s floor under an unauthenticated probe endpoint cannot be lowered by a mistimed or repeated release (task 1) |
| T-30-36-02 | Tampering | `_last_manual_claim` under concurrency | mitigate | the compare and the clear happen together under the existing `self._lock`, and a two-thread test exercises the window the previous argument only described (task 1) |
| T-30-36-03 | Denial of Service | probe rate through the collapse path | accept | a released claim still buys no probe: the collapse issued no Paperless request, no saned dial and no filesystem write, which is the existing and unchanged argument for why giving the claim back is safe |
| T-30-36-04 | Information Disclosure | the stamp crossing the API boundary | accept | the value is a monotonic-ish clock reading held in memory, never rendered, logged or returned to a client |
