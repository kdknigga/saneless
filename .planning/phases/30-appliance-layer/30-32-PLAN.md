<objective>
Make the checks poll's own failure end the checks poll, against the response this application
actually sends.

Purpose: `render_error` (`web/errors.py:177-178`) sets `HX-Retarget: #status-message` and
`HX-Reswap: innerHTML` on every htmx error response, unconditionally. The vendored
`htmx-2.0.8.min.js` applies `HX-Retarget` to `responseInfo.target` *before* the swap is acted on
(`if(T(n,/HX-Retarget:/i)){e.target=Un(t,...)}` precedes the `shouldSwap` block), so any 4xx/5xx
from `GET /api/checks` is swapped into `#status-message` and `#checks-body` is never replaced.
`#checks-body` keeps its `hx-trigger="every 2s"` and keeps polling for as long as the tab is open,
and every 2 s the failing poll overwrites `#status-message` -- the scan-progress slot the strip is
documented (D-03) to leave alone -- so a scan in progress has its progress line replaced by a
generic error sentence twice a minute.

`tests/test_browser.py::TestPollEndsOnAnErrorResponse` concludes "there is no defect" while driving
the failure with Playwright's client-side `route.fulfill()` and a hand-written body carrying **no
response headers** -- a response this application never sends -- so it cannot fail for the property
it is named after. `docs/reference/web-api.md:136` then states the disproved claim as shipped fact.

Output: an error renderer that exempts the strip's own swap target from the retarget, a checks
route that cannot raise into that renderer for an ordinary failure, a browser measurement driven by
the server, and documentation that describes the mechanism the code has.

## Out of scope

The poll's *window* -- whether ten attempts at 2 s is long enough for the worst-case probe, and
what the strip says when a chain runs out while a probe is demonstrably still running -- is
R3-WR-04 and belongs to plan 30-35, which owns the cap constants and `_checks_context`'s
`gave_up` branch. This plan changes neither the cap's value nor the give-up line's wording.
</objective>

<decision_record>
## Which of the three proposed fixes, and why

`30-REVIEW.md` and `30-VERIFICATION.md` enumerate three options. This plan implements the third
(**suppress `HX-Retarget`/`HX-Reswap` for a request whose target is the strip's swap target**) as
the fix, and the second (**the route stops producing errors for its own ordinary failure modes**)
as hardening on top of it. The first is rejected outright, because it does not work against the
bundle this application ships.

**Rejected: client-side `hx-on::response-error="this.removeAttribute('hx-trigger')"`.** Measured
against `src/saneless/web/static/vendor/htmx-2.0.8.min.js`: polling is armed once, by
`ct(e,t,n)`, which re-arms itself from a closure -- `r.timeout=setTimeout(function(){if(se(e)&&r.cancelled!==true){...;ct(e,t,n)}},n.pollInterval)`.
`se(e)` is `e.getRootNode({composed:true})===document`, i.e. "is the element still attached", and
`r.cancelled` is set only by `lt(e)`, which this bundle calls in exactly one place: the
`if(n.status===286)` branch inside the swap. The loop never re-reads the `hx-trigger` attribute, so
removing the attribute is a no-op against an already-armed poll. Shipping it would have produced a
third round of "a mechanism that reads as a fix and is not one", which is the precise failure this
round exists to stop.

**Rejected as the sole fix: the route catches its own failure and returns a 200 strip.** It cannot
cover the 422, because `attempt: Annotated[int, Query(ge=0, le=POLL_ATTEMPT_CAP)]` is rejected
during FastAPI request validation, before the handler body runs; the resulting
`RequestValidationError` goes to the app's handler and out through `render_error` with the
retarget headers attached. It also cannot cover a 405, a 429 or anything the framework raises. It
is, however, the better answer for the failures it *can* cover, which is why it is kept as
hardening: it leaves the five rows and the `Check again` button on the page instead of replacing
the strip with an error box.

**Chosen: exempt the strip's swap target from the retarget, and harden the route.** The exemption
is one condition in one function and it fixes every response-bearing failure path at once (422,
500, 404, 405, 429). Its mechanism is the one htmx actually implements: with no `HX-Retarget` the
response is swapped by the polling element's own `hx-target="this" hx-swap="outerHTML"`, the old
`#checks-body` is detached, `se(e)` is false on the next tick, and the chain ends. `base.html`'s
`{"code":"[45]..","swap":true,"error":true}` rule is what makes an error response swap at all, and
it is therefore load-bearing for this fix -- the existing test that pins that meta rule stays, with
its reasoning corrected.

**Known residual, stated rather than hidden:** a transport-level failure (the server gone, a
connection reset) produces no response at all, so neither mechanism fires and the poll continues
until `POLL_ATTEMPT_CAP`... which it never reaches, because the attempt counter only advances
through bodies the server swaps in. A tab whose appliance has gone away therefore keeps asking
every 2 s. That is a request to a dead origin -- no scan display to overwrite, no scanner traffic,
no Paperless traffic -- and closing it needs a client-side timer this application has no other
reason to own. It is recorded here and in `docs/reference/web-api.md` rather than left for a
fourth round to rediscover.
</decision_record>
