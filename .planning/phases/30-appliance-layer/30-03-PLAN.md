<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| web request -> job store | An opaque browser-supplied session token crosses into persistent storage |
| job store -> every reader | `owner_token` is a secret-shaped value that must never reach a rendered page or a log |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-09 | Information disclosure | `owner_token` stored on the job row | mitigate | The column is written and read only by the flip-gate comparison; no template renders it and no log statement in `job.py` includes it. Plan 30-13's template tests assert the token string never appears in rendered markup |
| T-30-10 | Spoofing | a guessed `owner_token` | accept | REQUIREMENTS states explicitly that the owner token is a footgun guard for the flip prompt, not an authentication mechanism; the trusted-LAN decision stands. Plan 30-13 still mints it with `secrets.token_urlsafe(32)` (>=128 bits) and compares with `secrets.compare_digest` |
| T-30-11 | Tampering | SQL for `queue_position` | mitigate | Parameterised query only; `job_id` is bound, never interpolated, matching every other statement in `job.py` |
| T-30-12 | Denial of service | dropping the `thumbnail` parameter | mitigate | Verified by grep that no caller passes it and `update_thumbnail` is the live writer; the signature test pins the parameter tuple so a silent re-add is impossible |
| T-30-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing |
</threat_model>
