**Evidence base.** Every mechanical claim below was read or measured on 2026-09-16 against this tree:

- htmx 2.0.8, from `src/saneless/web/static/vendor/htmx-2.0.8.min.js`:
  - `Lt(e) { return e.form || closest(e, "form") }` — htmx resolves an element's form through the **HTML form-owner IDL property**, so an `<input form="…">` is never gathered with its DOM-ancestor form.
  - `dn(e, t)`: `if (t !== "get") { include Lt(e) }` — a **GET** request does **not** auto-include the enclosing form. `hx-include` is therefore mandatory to carry checked tags on the filter request.
  - `sn(e)`: `if (t.type === "checkbox" || t.type === "radio") return t.checked` — an `hx-include` over a checkbox list sends only the **checked** boxes.
  - `hx-include` on a non-form target also gathers every descendant matching `"input, textarea, select"`.
  - `hx-confirm`, `keyup`, `changed`, `delay:` and `hx-params` (`not x` form) are all present in the bundle.
- PicoCSS 2.1.1, from `src/saneless/web/static/vendor/pico-2.1.1.min.css`:
  - `:where(input,select,textarea,fieldset,.grid)+small { display:block; width:100%; margin-top:calc(var(--pico-spacing)*-.75); margin-bottom:var(--pico-spacing); color:var(--pico-muted-color) }` — **a `<small>` immediately after a control is Pico's built-in help-text pattern.** This phase's help text needs no new CSS.
  - `[type=checkbox] { width:1.25em; height:1.25em }` (20 px) and `label:has([type=checkbox],[type=radio]) { width:fit-content }` — both are below a thumb target and both must be overridden for D-30.
  - `fieldset { width:100%; margin:0 0 var(--pico-spacing); padding:0; border:0 }` — a fieldset is an invisible grouping box, and it is in the `+small` selector list.
- Colour values and contrast ratios are **not re-measured**: every colour this phase renders is an existing token already Chromium-measured and asserted in `tests/test_browser.py`. The ratios are quoted from `.planning/UI-SPEC.md` § Measured status contrast.

## S1 — Status Strip (APPL-01, -02, -06, -11)

### Placement

The strip is the **first** `<article>` in `{% block content %}`, above the Scan card.

```
<main class="container">
  <article id="checks-card">   ← NEW (S1)
  <article>Scan …</article>
  <div id="status-message" role="alert"></div>   ← unchanged, still immediately precedes #status-area
  {% include "partials/status.html" %}
  <article>Job History …</article>
```

Three reasons, in order:
1. The phase goal is that a household member can tell **at a glance** whether the appliance is healthy. At a glance means first.
2. It is **outside `<form hx-post="/api/scan">`**, so the `hx-disabled-elt` / `hx-disinherit` landmine (Pitfall 8) cannot reach it. **This phase adds no attribute to the `<form>` element; `hx-disinherit="hx-disabled-elt"` stays exactly as written today.**
3. Phase 26's invariant — `#status-message` is the immediate sibling above `#status-area` — is preserved untouched.

**Accepted cost:** on a 375 × 667 phone the five rows (~160 px plus card padding) push the Scan button below the fold by roughly one short scroll. The strip is not collapsed to a summary when everything is green, because success criterion 1 requires the index page to show *the same checks* `saneless doctor` prints.

### Structure

`#checks-strip` is a **persistent live region**; `#checks-body` is the swap target. This mirrors Phase 26's accessibility rule (the container survives, its children are replaced), and it is what lets the cold-start poll stop itself.

```html
<article id="checks-card">
  <h2>System status</h2>
  <div id="checks-strip" aria-live="polite">
    {% include "partials/checks.html" %}
  </div>
</article>
```

`partials/checks.html` (the whole swap target):

```html
<div id="checks-body"
     {% if checks is none %}
     hx-get="/api/checks" hx-trigger="load, every 2s" hx-target="this" hx-swap="outerHTML"
     aria-busy="true"
     {% endif %}>
  <ul class="check-list">
    {% for c in checks or checking_rows %}
    <li class="check-row">
      <span class="check-glyph {{ c.state | check_state_class }}" aria-hidden="true">{{ c.state | check_state_glyph }}</span>
      <span class="sr-only">{{ c.state | check_state_label }}:</span>
      <span class="check-name">{{ c.key | check_name }}</span>
      <span>
        {{ c.message }}
        {% if c.next_step %}<span class="check-next">{{ c.next_step }}</span>{% endif %}
      </span>
    </li>
    {% endfor %}
  </ul>
  <p class="check-meta">{{ freshness_line }}</p>
  <button type="button" class="check-refresh secondary"
          hx-post="/api/checks/refresh" hx-target="#checks-body" hx-swap="outerHTML">Check again</button>
</div>
```

Rules:
- **Cold start (D-06):** when the cache holds no results, five `Checking…` rows render and the body carries `hx-trigger="load, every 2s"`. The swapped-in body has results, therefore no trigger, therefore polling stops. This is the in-tree idiom (`status.html` lines 1–6) — **do not use HTTP 286**, which would need a change to the tuned `htmx-config` meta.
- **Never a steady-state poll.** Once results land the strip is refetched only by (a) `Check again`, (b) the terminal-state reload below, (c) a page load. A permanent poll would keep D-05's lazy refresher awake for every abandoned browser tab, which is exactly what D-05 forbids.
- **Paused → un-paused promptly (D-08).** `POST /api/scan` success carries an out-of-band `#checks-body` (flag `refresh_checks`, set only by `start_scan`, exactly parallel to Phase 26's `clear_message`), so the paused note appears at once. Every terminal branch of `status.html` includes `partials/terminal_reload.html`, which holds the existing hidden history loader **plus** a hidden `hx-get="/api/checks" hx-target="#checks-body" hx-swap="outerHTML" hx-trigger="load"` loader, so the strip un-pauses the moment the scan ends instead of waiting out the TTL.
- The strip carries **no `role="alert"`**. `aria-live="polite"` only: a health list must never interrupt, and Phase 26 requires exactly one assertive region on the page.
- Templates own no vocabulary: `check_row_class`, `check_row_glyph`, `check_row_label`, `check_name` are the Jinja filters the rows are drawn with, registered beside `state_label` in `web/app.py` and implemented in `checks.py`. The three `check_state_*` lookups stay registered and are what the row filters delegate to, but the template reaches for none of them directly — a row's marker is chosen from the whole `CheckResult`, `skipped` flag included (R3-WR-03).

### The five rows

Name column is a separate element, so the existing `connection_status_message` sentences drop in **verbatim** (D-02) with no string surgery and no capitalisation collision.

| Name | State | Message | Next step (`.check-next`, WARN/FAIL only) |
|---|---|---|---|
| Scanner | OK | `{device} is ready.` (or `Ready.` when the backend reports no name) | — |
| Scanner | FAIL | `Not reachable.` | `Check the scanner is switched on and connected, then press Check again.` |
| Scanner | FAIL | `Scanner support is not installed on this machine.` (A-1) | `Install saneless with scanner support, then restart it.` |
| Scanner | skipped (D-08) | `Not checked while a scan is running.` | — |
| Scanner | skipped (R2-WR-02) | `The scanner was busy, so it was not checked this time.` | — |
| Paperless | OK | `Connected to paperless-ngx.` | — |
| Paperless | FAIL | `The paperless-ngx API token has not been set.` (placeholder, D-14/D-15) | `Put a real API token in the saneless config file, then restart saneless.` |
| Paperless | FAIL | `Paperless-ngx rejected the API token.` | `Check the API token in the saneless config file, then restart saneless.` |
| Paperless | FAIL | `The paperless-ngx API was not found at that URL.` | `Check the paperless-ngx address in the saneless config file.` |
| Paperless | FAIL | `Paperless-ngx returned a server error.` | `Check paperless-ngx is healthy, then press Check again.` |
| Paperless | FAIL | `Could not reach paperless-ngx.` | `Check paperless-ngx is running and on the network, then press Check again.` |
| Profiles | OK | `{n} scan profiles configured.` (`1 scan profile configured.`) | — |
| Profiles | FAIL | `No scan profiles are configured.` | `Run "saneless auto-profiles" to create them.` |
| Profiles | WARN | `Generated in memory — the config location is read-only, so they are lost on restart.` (D-22, verbatim) | `Make the saneless config directory writable, then restart saneless.` |
| Profiles | WARN | `Generated in memory — no configuration file is in use, so they are lost on restart.` | `Create a saneless config file so the profiles are saved.` |
| Profiles | WARN | `Some profiles have no name yet.` (A-3) | `Run "saneless auto-profiles --force" to name them.` |
| Fallback | OK | `A folder is set up to keep scans if paperless-ngx is down.` | — |
| Fallback | WARN | `Not configured; scans cannot be kept if paperless-ngx is down.` (APPL-11) | `Set a fallback folder in the saneless config so scans are kept when paperless-ngx is down.` |
| Fallback | FAIL | `The fallback folder cannot be written to.` | `Check the folder exists and saneless can write to it.` |
| Data folder | OK | `The data folder is writable.` | — |
| Data folder | FAIL | `The data folder cannot be written to.` | `Check the folder exists and saneless can write to it, then restart saneless.` |
| *(any)* | cold start | `Checking&#8230;` | — |

**The two `skipped` rows render the neutral marker, not the state's (D-08, R3-WR-03).** A skipped row carries `CheckState.OK` so that `saneless doctor` keeps exiting 0 for a probe that was deliberately not taken (D-01) — the state is there to give the row a colour, not to report a verdict. It is therefore drawn with the cold-start glyph `·` and the cold-start class `check-checking`, and announced to a screen reader as **`Not checked:`** (`SKIPPED_STATE_LABEL`), *not* as `OK:` and not as `Checking:` — a listener told "Checking" over a row nobody probed is told a probe is running when none is. The choice is made in Python, by `check_row_class` / `check_row_glyph` / `check_row_label`, which take the whole `CheckResult`; the template reaches for those three and for none of the `check_state_*` filters. `saneless doctor` reads the same flag through `_row_marker` and prints `[SKIP]` (see § CLI parity).

Precedence inside the Profiles check, when more than one condition holds: `FAIL (none configured)` → `WARN (unwritable)` → `WARN (no config file)` → `WARN (no names)` → `OK`. A check returns exactly one `CheckResult`.

**No path, URL, token or exception text appears in any row.** The fallback row deliberately omits the folder path, for the same reason D-13 omits the log path: it is a host filesystem path on a LAN-visible page. The Paperless rows never render the URL (it may carry `user:pass@` — `paperless.py:461`) and never render the token value.

### Freshness line (D-08, D-35)

| Situation | `.check-meta` copy |
|---|---|
| Cold start, no scan running | `Checking&#8230;` |
| Cold start, scan running | `Paused during scan — not checked yet.` |
| Results, no scan running | `Last checked {{ checked_at \| local_time }}.` |
| Results, scan running | `Paused during scan — last checked {{ checked_at \| local_time }}.` |

The em dash is `—` (U+2014) with spaces, as in D-08's specimen. The timestamp is the shared `local_time` filter (S7), so it reads `Last checked 2026-09-16 14:02 CDT.`

### `Check again` (D-09)

- Visible text `Check again`, **not** an icon-only control: a household member is the reader. Pico `.secondary`, because accent is reserved for the primary Scan button.
- Pico's button height is `1rem × 1.5 + 0.75rem × 2 + 2 × border` ≈ 50 px, so it already exceeds 44 px; `.check-refresh { width: auto }` stops Pico's full-width default.
- `hx-post="/api/checks/refresh"` → `#checks-body`, `outerHTML`. `CrossOriginGuard` covers it automatically (app-wide middleware; no per-route dependency).
- During a scan it re-runs only the non-scanner checks and the Scanner row keeps its skipped message.

### CLI parity (D-02)

`saneless doctor` prints one line per check from the **same registry, same message strings, same next steps**, as `[ OK ] Scanner  <message>` / `[WARN]` / `[FAIL]`, with the next step on an indented second line for `WARN` and `FAIL`. Neither surface may hold a message the other does not.

## S2 — Plain-Language Errors (APPL-04, D-10..D-13)

### The seven next steps (new copy, developer constants)

`error_advice(category) -> ErrorAdvice(message, next_step)`. The **messages are the existing `vocabulary.error_message` strings, unchanged**. Only `next_step` is new. Both surfaces (web and CLI) render the same string, so the wording is **surface-neutral** — never "press Scan", never "run the command".

| `ErrorCategory` | `message` (existing, unchanged) | `next_step` (new) |
|---|---|---|
| `FEEDER` | The document feeder is empty or jammed. | `Load the pages squarely in the feeder, clear any jam, then start the scan again.` |
| `CONFIG` | The saneless configuration is invalid. | `Correct the saneless configuration file, then restart saneless.` |
| `SCANNER` | The scanner could not complete the scan. | `Check the scanner is switched on and connected, then start the scan again.` |
| `UPLOAD` | The document could not be sent to paperless-ngx. | `Check paperless-ngx is running and the API token is correct, then start the scan again.` |
| `ASSEMBLY` | The scanned pages could not be assembled into a PDF. | `Start the scan again. If it keeps failing, check the server's free disk space.` |
| `REJECTED` | This scan was not started. Check that saneless is ready to scan, then try again. | `Check the system status list for anything marked Failed, then start the scan again.` |
| `UNKNOWN` | Something went wrong. | `Start the scan again. If it keeps failing, check the saneless log.` |

Style: sentence case, imperative, one sentence (two for `ASSEMBLY`/`UNKNOWN`), ends with a period, no exclamation mark, no emoji — the inherited copy guide.

### Status-area `ERROR` branch (`partials/status.html`)

```html
{% elif job.state == JobState.ERROR %}
  {% if job.error_category %}
    <div role="alert">
      <p class="status-error">&#10007; {{ job.error_category | error_message }}</p>
      <p>{{ job.error_category | error_next_step }}</p>
    </div>
    <details class="tech-details">
      <summary>Technical details</summary>
      <p>{{ job.error }}</p>
      <p>Category: {{ job.error_category }}</p>
      <p>Job: {{ job.id }}</p>
    </details>
  {% else %}
    <p role="alert" class="status-error">&#10007; Error: {{ job.error }}</p>
  {% endif %}
  {% include "partials/terminal_reload.html" %}
```

Contract:
- **`role="alert"` moves from the `<p>` to a wrapping `<div>`** so the alert covers the plain sentence **and** the next step. The next step is the most actionable content on the page; leaving it outside the alert would mean a screen-reader user never hears it. Exactly **one** alert region remains in the status area, and the `<details>` sits outside it so "Technical details" is not announced with the failure.
- The `<p class="status-error">` keeps the `✗` glyph and the `.status-error` class. It loses the literal `Error: ` prefix, because the sentence now names the problem itself.
- **The specific message is not removed, it is relocated.** `vocabulary.error_message`'s docstring warns that swapping the specific message for a category sentence is a regression; CONTEXT resolves this — APPL-04 *adds* the category sentence and the next step, and `job.error` is still rendered, inside the disclosure. `job.error` storage is unchanged.
- **The log file path is never rendered** (D-13). A grep assertion belongs in the plan: no template under `web/templates/` references a log path.
- **A NULL `error_category`** (a row written before Phase 21) renders today's shape verbatim, with no next step and no disclosure. Substituting `UNKNOWN` would print "Something went wrong." over a row that still holds a truthful specific message.
- `tests/test_web_state_rendering.py:247` pins the old exact string and **must be rewritten in this phase**. That is a legitimate "could not have passed before" test.

### Request-error slot (`partials/error.html`)

```html
<p class="status-error">&#10007; {{ message }}</p>
<details class="tech-details">
  <summary>Technical details</summary>
  <p>Status: {{ status_code }}</p>
  {% if job_id %}<p>Job: {{ job_id }}</p>{% endif %}
</details>
{% if refresh_history %}<div hx-get="/api/jobs/history" hx-target="#history-body" hx-swap="outerHTML" hx-trigger="load" class="htmx-hidden"></div>{% endif %}
```

- Phase 26's twelve slot messages are **unchanged**. Each is already "the problem, then what to do next" in one sentence pair, so APPL-04's message-plus-next-step requirement is already met by the string; splitting a locked, doc-pinned copy table would be churn with no reader benefit.
- The disclosure is deliberately short. The HTTP status code and the rejected job's id are the **only** technical facts the slot is permitted to carry: Phase 26 D-10 and ASVS V7 forbid exception text, request input and the log path from ever reaching this surface. Saying so is better than a uniform affordance that sometimes lies about having detail.
- Still **no `role="alert"` inside the partial** — `#status-message` is the alert region (`tests/test_web_errors.py:243` guards this and still passes).
- `tests/test_web_errors.py:206` and `tests/test_cross_origin.py:356` assert the response body equals the old single `<p>` **exactly** and must be updated in this phase. Budget for both.

## S3 — Page Counts (APPL-03, D-32, D-33)

### The sentence

Built by one shared helper, `page_counts(job) -> str | None`, registered as a Jinja filter (templates own no vocabulary). It returns `None` unless **all three** counts are non-`NULL`.

| Case | Rendered |
|---|---|
| 12 / 2 / 10 | `12 pages scanned, 2 blank removed, 10 uploaded` |
| 1 / 0 / 1 | `1 page scanned, 0 blank removed, 1 uploaded` |
| any count `NULL` | **nothing at all** — no element, no empty line |

- Only the first clause pluralises (`page` / `pages`); the other two carry no noun.
- **A measured `0` renders as `0`.** D-32's "never render 0" is about `NULL`, not about a true zero: a scan where nothing was blank really did remove 0 pages. The Jinja guard is `is not none`, never truthiness (Pitfall 4). Four of six terminal cases are `NULL` (`ERROR`, `CANCELLED`, `REJECTED`, pre-Phase-23 rows), so this is the common path, not an edge.
- **Success criterion 3 means "every terminal job that recorded counts".** `ERROR` and `CANCELLED` rows have no counts by construction (`worker.py:1348-1352`), and D-32 accepts that.

### Status area

The counts are the **last paragraph of the terminal branch**, after the outcome line and after `FALLBACK`'s warning line, before the thumbnail:

```html
<p class="status-done">&#10003; Done: {{ job.title }}</p>
{% set counts = job | page_counts %}
{% if counts %}<p class="page-counts">{{ counts }}</p>{% endif %}
```

Same shape under `FALLBACK`. Not rendered under `ERROR`, `CANCELLED` or the idle branch.

### History table — **a second line in the Title cell, not a fifth column**

```html
<td>{{ job.title }}{% set counts = job | page_counts %}{% if counts %}<span class="page-counts">{{ counts }}</span>{% endif %}</td>
```

Decision and reasons (CONTEXT left this to the planner; the brief requires it decided here):
- **No `colspan` drift.** The four `<th>`s in `index.html:76-81` and `colspan="4"` in `history.html` stay as they are — Pitfall 11 is designed out rather than guarded against.
- **It works on a phone.** The existing `@media (max-width: 576px)` rule already gives `#history-body td` `white-space: normal; word-break: break-word`, so a two-line Title cell wraps correctly with no new breakpoint. A fifth column would compete with the Time column, which S7 simultaneously widens.
- `.page-counts` is `display: block`, so the counts form their own line in both the table cell and the status area, with **one** class and **one** rule.
- The counts line is **not** wrapped in `<small>`. Inside the table the mobile rule already reduces the cell to `0.875rem`; a nested `<small>` would compound to ~12 px and create a fifth type size. It renders at the cell's own size, distinguished by colour alone.

```css
/* The page counts are a quiet second line under the outcome, in the status
   area and in the Title cell alike. Muted, never a status colour: a count is
   a measurement, not an outcome. */
```

### Manual duplex, pass B (D-33)

```html
<label for="profile-select">Profile</label>
<select name="profile" id="profile-select"
        aria-describedby="profile-description"
        hx-get="/api/profiles/description"
        hx-trigger="change"
        hx-target="#profile-description"
        hx-swap="innerHTML">
```

Contract:
- **The control stays a `<select>`** (D-20). Not a radio group.
- **`{{ p.label or p.name }}`** — Amendment A-3. A deployed config whose profiles predate this phase has `label = ""`, and a blank option is worse than a raw profile name. The how-to guide says `saneless auto-profiles --force` backfills the names.
- **`value` stays the profile name.** It is the wire contract `POST /api/scan` already uses; only the option *text* changes.
- **Ordering (D-21):** when the device reports no flatbed source (`has_flatbed` false — the literal definition of sheet-fed), feeder profiles are emitted first. Within each group, existing config order is preserved. No `<optgroup>`: it adds a second visual level for at most two groups.
- **Generated description text (D-19):** `Feeder, single-sided` / `Feeder, double-sided` / `Glass (flatbed)` are the **labels**; the `description` is the sentence beneath, e.g. `Scans both sides of every page using the document feeder.` Both are derived from `SourceKind` and `duplex`, from facts the code already has. No new probe.
- **`hx-swap="innerHTML"`, never `outerHTML`.** The `<small>` must survive the swap: it carries the `id` that `aria-describedby` points at, the `aria-live="polite"` region, and Pico's `select + small` adjacency that gives it its muted styling. Replacing the element would break all three. The route returns `partials/profile_description.html`, which is the text alone.
- **The description doubles as the Profile control's one line of help text** (APPL-10). There is no second help line under Profile.
- The select's own `name="profile"` value rides the GET automatically (htmx includes the triggering input's own value), so the route reads `profile` as a **query parameter validated against the known profile set** — 422 on an unknown name, matching `routes.py:420-423`. No path parameter, therefore no traversal surface.
- The select is inside `<form hx-post="/api/scan">` and inherits nothing harmful: it sets no `hx-disabled-elt` of its own and the form's existing `hx-disinherit="hx-disabled-elt"` covers it.

```css
/* A profile with no description would otherwise leave Pico's help-text
   margins behind as a stray gap. */
#profile-description:empty {
    display: none;
}
```

## S5 — Queue Position and the Owner-Gated Flip Prompt (APPL-08, -09)

### Queue position (D-25)

The status area follows **the job this browser submitted** (the `POST /api/scan` response bakes the id into the poll URL, `hx-get="/api/jobs/{{ job.id }}/status"`; a browser that submitted nothing keeps today's `GET /api/jobs/current/status` and today's current-or-most-recent inference). When the followed job is `PENDING` and another job is running, `busy_line` is:

| Condition | Copy |
|---|---|
| N ≥ 1 jobs ahead | `Waiting for 'Tax return' to finish (1 ahead of you)` |
| 0 jobs ahead | `Waiting for 'Tax return' to finish (next in line)` |
| `PENDING`, nothing running | `Starting scan...` (unchanged) |

`(0 ahead of you)` is never rendered — it is technically true and reads like a bug. Single quotes around the title, exactly as APPL-08 writes it. The title is user data and is autoescaped; it is never truncated (the line wraps). Rendered in the existing busy branch with `aria-busy="true"`; no new state branch.

### Owner gate (D-23, D-24)

`partials/status.html`'s `AWAITING_FLIP` branch becomes three-way:

```html
{% if flip_answer %}
  <p aria-busy="true">{{ flip_answer | flip_answer_label }}</p>
{% elif is_owner %}
  {% include "partials/flip.html" %}
{% else %}
  <p aria-busy="true">Waiting for the stack to be flipped</p>
{% endif %}
```

- Non-owner copy is **verbatim** from D-24, with no trailing ellipsis, even though the in-progress copy style normally ends `...`. The user wrote this string twice; it is treated as locked copy and the style exception is recorded here.
- **Everything else is identical for both viewers** — state, title, page counts, thumbnail, errors. Only Continue and Abort are gated.
- **Server-side gate only.** The buttons are *not rendered* for a non-owner. Hiding them with CSS would be an ASVS V4 failure and is forbidden.
- **A `NULL` `owner_token` means unowned: render the prompt for everyone.** Every row written before this phase has `owner_token IS NULL`, including a manual-duplex job in flight across an upgrade. A strict rule would make such a job un-continuable and force it to time out. Nothing can create a `NULL`-token job after this phase, so the rule has a closed lifetime.
- The owner cookie itself has no UI: `HttpOnly`, `SameSite=Lax`, no `Max-Age`, never rendered into HTML, never logged. There is no script file that could read it.

### Abort confirmation (D-27)

```html
<button hx-post="/api/flip/abort"
        hx-vals='{{ {"job_id": job.id} | tojson }}'
        hx-target="#status-area" hx-swap="outerHTML"
        hx-confirm="Abort this scan? It will stop and cannot be resumed."
        class="secondary">Abort scan</button>
```

- Exact confirmation copy: **`Abort this scan? It will stop and cannot be resumed.`** One question, one consequence, and it asserts nothing the code does not guarantee. It deliberately does **not** claim the already-scanned pages are kept — that would be a promise this contract cannot verify, and unverifiable promises are what this milestone removes.
- `hx-confirm` goes on the **button**, which lives in `flip.html`, **outside** `<form hx-post="/api/scan">`. Putting it on the form would make every child request confirm and would require extending `hx-disinherit` (Pitfall 8). It is not on the form.
- The native `window.confirm` dialog is unstyled and fully accessible: focus-trapped, keyboard-operable, announced by every screen reader. No modal partial, no extra route, no script.
- Button label stays `Abort scan`; Pico `.secondary`, not a destructive red.
- **This reverses a documented master decision.** `.planning/UI-SPEC.md` § Deliberate design decisions records "Abort scan has no confirmation dialog" as intentional. D-27 supersedes it; the master spec must be edited (see § Master UI-SPEC Edits).

## S6 — Form Help Text and the Tag Picker (APPL-10, D-28..D-31)

### Help text — Pico's built-in pattern, zero new CSS

A `<small>` **immediately following** a control is Pico's help-text pattern: block, full width, `--pico-muted-color`, `0.875em`. One line per control, each wired with `aria-describedby`.

| Control | Help line |
|---|---|
| Profile | *(the live description, S4)* |
| Title | `What this document should be called in paperless-ngx.` |
| Tags (fieldset) | `Labels to file this under in paperless-ngx. Optional.` |
| Filter tags | `Type to narrow the list. Ticked tags stay ticked.` |
| Correspondent | `Who sent this document? Optional.` *(D-28 specimen, verbatim)* |

The Title `placeholder` (`Document title (auto-generated if empty)`) is unchanged; the help line says something different, so the two do not repeat each other. Contrast for `--pico-muted-color` on the card surface: **5.36:1 light, 4.53:1 dark** — AA pass, already asserted by the existing `card` placement parametrisation in `tests/test_browser.py`.

### The Tags block — exact markup

```html
<fieldset aria-describedby="tags-help">
    <legend>
        Tags
        <button type="button"
                hx-post="/api/cache/invalidate?resource=tags"
                hx-target="#tags-list" hx-swap="outerHTML"
                hx-include="#tag-filter, #tags-list"
                class="refresh-btn" title="Refresh tags"
                aria-label="Refresh tags">&#x21bb;<span class="sr-only">Refresh tags</span></button>
    </legend>

    <input type="search" id="tag-filter" name="q" form="tag-filter-form"
           placeholder="Filter tags"
           aria-describedby="tag-filter-help"
           hx-get="/api/tags" hx-target="#tags-list" hx-swap="outerHTML"
           hx-trigger="keyup changed delay:300ms"
           hx-include="#tags-list">
    <small id="tag-filter-help">Type to narrow the list. Ticked tags stay ticked.</small>

    <div id="tags-list" class="tag-list"
         hx-get="/api/tags" hx-trigger="load" hx-target="this" hx-swap="outerHTML">
        {% include "partials/tags.html" %}
    </div>
</fieldset>
<small id="tags-help">Labels to file this under in paperless-ngx. Optional.</small>
```

and, as a **sibling after `</form>`**, still inside the Scan `<article>`:

```html
{# The filter box belongs to this form, not to the scan form. An input with a
   form attribute is owned by the form it names, so the filter text is never
   submitted with a scan and pressing Enter in it filters the list instead of
   starting one. This form is empty and has no submit button; htmx handles its
   submit event and sends the same request the debounced keyup sends. #}
<form id="tag-filter-form" class="htmx-hidden"
      hx-get="/api/tags" hx-target="#tags-list" hx-swap="outerHTML"
      hx-include="#tags-list"></form>
```

`partials/tags.html` renders the whole swap target's children:

```html
{% for tag in pinned %}
<label class="tag-option"><input type="checkbox" name="tags" value="{{ tag.id }}" checked> {{ tag.name }}</label>
{% endfor %}
{% for tag in tags %}
<label class="tag-option"><input type="checkbox" name="tags" value="{{ tag.id }}"{% if tag.id in selected %} checked{% endif %}> {{ tag.name }}</label>
{% endfor %}
```

### How this solves A-5 and A-6

**A-5 — a filter swap must not lose ticked tags.**
- `hx-include="#tags-list"` on the filter input. Verified in the vendored bundle: an `hx-include` whose target is not a form gathers every descendant matching `"input, textarea, select"`, and `sn()` includes a checkbox **only when `checked`**. So the request carries `q=rec&tags=3&tags=7` — exactly the current selection, nothing else.
- The route re-renders every id in `tags` as `checked`, and **pins selected tags that fall outside the filter above the filtered list** (`pinned`), so a tick can never vanish from the DOM and therefore can never be silently dropped from the next submit.
- `q` is used only as a Python-side `in` filter over the already-cached `MetadataCache` list. It is **never** interpolated into a paperless-ngx query URL and **never** echoed back into the response (ASVS V5).

**A-6 — a named filter input inside the scan form must not be submitted with the scan.**
- `form="tag-filter-form"` makes the input's HTML **form owner** the filter form, not the scan form, even though it is DOM-nested inside it. htmx resolves the form as `e.form || closest(e,'form')`, and gathers a form's values with `form.elements` and `new FormData(form)` — all three honour the form-owner association. `POST /api/scan` therefore **cannot** carry `q`, independent of whether FastAPI tolerates unknown form fields (research assumption A4 is designed out rather than relied on).
- It also removes a real footgun the research did not name: an `<input type="text">` inside a form with a submit button triggers **implicit submission** on Enter. Without the `form` attribute, a household member typing a tag filter and pressing Enter would **start a scan**. With it, Enter performs implicit submission of `tag-filter-form`, which htmx intercepts and turns into the same filter request. Enter filters; it never scans.
- **Nothing is added to the `<form hx-post="/api/scan">` element.** `hx-disinherit="hx-disabled-elt"` is unchanged, so the C-10 landmine is untouched. This is the decisive advantage over the alternative (`hx-params="not q"` on the form, which would have required extending the disinherit list).

### Touch targets (D-30)

```css
/* Tag picker: the label is the tap target, so the whole row toggles the box.
   Pico shrinks a checkbox label to the width of its text and draws the box at
   1.25em, which is far under what a thumb needs, so the app owns both. The
   selector is label.tag-option, not .tag-option: Pico's own
   label:has([type=checkbox]) rule has the same weight, and app.css loads
   second, so a tie is what makes this win. */
label.tag-option {
    display: flex;
    align-items: center;
    gap: 0.5rem;
    width: 100%;
    min-height: 2.75rem;
    margin-bottom: 0;
    cursor: pointer;
}

.tag-list {
    max-height: 17.5rem;
    overflow-y: auto;
    margin-bottom: var(--pico-spacing);
}
```

- `min-height: 2.75rem` = **44 px** at a 16 px root, full row width. Rows are contiguous, which WCAG permits because each one is itself ≥ 44 px.
- `.tag-list` scrolls after roughly six rows; it contains focusable children, so it needs no `tabindex` (WCAG 2.1.1).
- **The checkbox glyph itself is not resized.** Pico's 20 px box inside a 44 px label is the standard accessible pattern and keeps the checked-state styling Pico owns.
- The checkbox list **replaces the multi-select everywhere** (D-30). `<select name="tags" multiple>` is deleted; there is one control, one partial, one set of tests.
- **Accepted limit:** the tag and correspondent `.refresh-btn` glyphs stay at their existing ~24 px inline size. They meet WCAG 2.5.8 (24 × 24, AA) and are maintenance controls, not scan-flow controls. The strip's `Check again` and the `Technical details` summary do get 44 px, because a household member taps those.

### The simpler form (D-28, D-29)

- `show_tags = false` → the entire Tags `<fieldset>`, both `<small>` help lines and `<form id="tag-filter-form">` are **absent from the rendered page**. Not hidden with CSS.
- `show_correspondent = false` → the Correspondent label, select and help line are absent.
- With both off the form is Profile, Title, Scan.
- **The scan is unchanged**: the profile's `default_tags` and `default_correspondent` still apply (D-29). Hiding a control changes the form, not the scan.
- This is a config key, not a per-browser toggle: one appliance, one form shape.

## S8 — Placeholder-Token Refusal: the Disabled Scan Button (APPL-07, D-14, D-15)

D-15: "The web layer refuses with a new `RequestRejection` member plus a disabled Scan button… **The route guard is the enforcement; the button is the courtesy.**" This section renders the courtesy. It never substitutes for the guard.

### The one blocking condition

**Exactly one condition disables the Scan button in this phase: a blank, whitespace-only, or literal-set placeholder paperless-ngx API token (D-14).** No other red check disables it. A scanner that is unreachable, a paperless-ngx that is down, an unwritable data folder — none of these block a submit. The user is allowed to try, and if it fails they get S2's plain-language error with a next step. Only the placeholder token is *certain* to make an upload impossible before any paper moves, which is the same test `saneless scan` applies at D-16. Do not generalise this to "any FAIL check".

### Button markup

`partials/scan_button.html` stays the **only** copy of the button markup, and `type="submit" id="scan-btn"` stay the **first two attributes in that order** (`tests/test_web_state_rendering.py::_SCAN_BUTTON` pins it). It gains one input — a `scan_blocked` flag read from server state — and one conditional attribute:

```html
<button type="submit" id="scan-btn"{% if oob %} hx-swap-oob="true"{% endif %}
        {% if scan_blocked %}aria-describedby="scan-blocked-reason"{% endif %}
        {% if scan_blocked or (job and job.is_active) %}disabled{% endif %}{% if job and job.is_active and job.is_busy %} aria-busy="true"{% endif %}>
    {% if job and job.state == JobState.AWAITING_FLIP %}Waiting for flip&#8230;{% elif job and job.is_busy %}Scanning&#8230;{% else %}Scan{% endif %}
</button>
```

### State table — one row added to 26-UI-SPEC S4

Phase 26's table is keyed on the job (current, else most recent run job) and is **unchanged**. `scan_blocked` adds a second, independent source of `disabled`; it does not touch the label or `aria-busy`.

| Condition | `disabled` | `aria-busy` | Label | `aria-describedby` | Reason line |
|---|---|---|---|---|---|
| **blocked, no job active** | **present** | absent | **`Scan`** | `scan-blocked-reason` | rendered |
| **blocked, job active** | present | per job state | per job state | `scan-blocked-reason` | rendered |
| not blocked | per Phase 26's table, unchanged | unchanged | unchanged | absent | absent |

- **The label stays `Scan`.** A disabled control plus a red line beneath it already says "you cannot do this, and here is why". Renaming it to `Cannot scan` would add a fourth label string and dissolve the single-word CTA the master spec deliberately keeps.
- `disabled` is a single boolean with two sources. Precedence questions do not arise: `disabled` is the OR, and the label and `aria-busy` come from the job, unchanged.

### The reason line

Rendered by `index.html` immediately after the `scan_button.html` include, inside the form, **only when blocked**:

```html
{% include "partials/scan_button.html" %}
{% if scan_blocked %}<small id="scan-blocked-reason" class="status-error">{{ scan_blocked_reason }}</small>{% endif %}
```

```css
/* Why the Scan button is greyed out, on its own line beneath it. A disabled
   button cannot be focused or reliably hovered, so the reason has to be
   visible text rather than a tooltip. */
#scan-blocked-reason {
    display: block;
    margin-top: 0.5rem;
}
```

- **Copy, verbatim:** `The paperless-ngx API token has not been set — see System status above.`
- It is a developer constant. It **never** interpolates the token value, the paperless-ngx URL (which may carry `user:pass@`) or exception text — ASVS V7, same rule as every other string in this phase.
- It deliberately does **not** repeat the fix. The strip's Paperless row, a few centimetres above, already carries `Put a real API token in the saneless config file, then restart saneless.` as its next step. Three surfaces name the same problem in the same words; only one owns the remedy.
- `.status-error` on the card surface: **7.83:1 light, 5.60:1 dark** — AA pass, already measured and asserted. No new colour.
- **Not a `title` tooltip and not `aria-disabled`.** A `disabled` button is not focusable, so `aria-describedby` on it is never announced on focus and a tooltip is unreachable by keyboard and unreliable on touch. The reason is therefore plain visible text in the reading order directly after the button; `aria-describedby` is kept only so an AT user exploring the form by element still reaches it. Switching to `aria-disabled="true"` to keep the button focusable is **forbidden**: it would break Phase 26's `disabled` contract and `hx-disabled-elt`.

### What flips it, and why nothing needs to flip it live

The placeholder verdict is derived from `Settings`, which is loaded once at process start. **It cannot change while the process runs**, so no live flip exists or is needed:

| Response | How the blocked state gets there |
|---|---|
| `GET /` (full page) | `scan_button.html` rendered inline from server state; the reason line rendered beside it |
| `POST /api/scan` success, status poll, flip continue/abort (every OOB `#scan-btn`) | the same partial, the same flag, re-read from server state every time — so **no** OOB re-render can ever hand back an enabled button |
| `POST /api/checks/refresh` | carries **no** OOB `#scan-btn` and **no** OOB reason line. Re-running the checks cannot change the verdict, so re-rendering the button would be theatre |
| anything else | unchanged |

`#scan-blocked-reason` is therefore **never** an out-of-band swap target and never needs to exist as an empty placeholder. It is present exactly when it has something to say.

**This is why the flag lives in `scan_button.html` and nowhere else.** On htmx 2.0.8 an inherited `hx-disabled-elt` strips `disabled` from a server-disabled button the moment a child request finishes — C-10, fixed only in 2.0.9, and htmx 4 is out of scope. The Scan button is therefore re-rendered from server state on every status response (ROBU-04), and `hx-disinherit="hx-disabled-elt"` on the form must not be removed or "tidied". If the blocked state were expressed anywhere other than the single button partial, the first tag or profile-description request to complete would re-enable it.

### The guard, not the button, is the enforcement

- `POST /api/scan` refuses **unconditionally** when the token is a placeholder, via a **new `RequestRejection` member**, and writes a `REJECTED` job row (Phase 26 D-05) so the attempt is visible in Job History. The refusal holds for curl, for a script, and for a browser whose `disabled` attribute was removed in devtools.
- `WORKER_DEGRADED` is **not** reused (D-15): saying "the scan service was unavailable" when the truth is "nobody set the token" is exactly the untruthfulness this milestone removes.
- Slot message for the new member, in Phase 26's established shape (problem, then next step, full sentence, ends with a period):
  **`The paperless-ngx API token has not been set, so the scan was not started. Put a real API token in the saneless config file, then restart saneless.`**
- Job-row `error` text for the `REJECTED` row, in the established shape (no trailing period): **`Not started: the paperless-ngx API token has not been set`**
- Status code: **503**. It matches the two existing refuse-to-start rejections, so htmx response handling and the history-refresh behaviour are identical; a `4xx` would imply the *request* was at fault, which it was not. The code is surfaced only inside S2's `Technical details` disclosure.

### The amber `warn` token — following 23.1's convention

The `warn` state reuses `--saneless-status-fallback` (`#a16207` light, `#ca8a04` dark). 1. App-owned scheme-dependent colour lives in a `--saneless-*` custom property declared on `:root` with its light value. **Already true, unchanged.**
2. Its dark value is declared twice, mirroring Pico's own selectors. **Already true, unchanged.**
3. Consuming rules read only the property, never a hex. **`.check-warn { color: var(--saneless-status-fallback); }`** — satisfied.
4. Pico tokens that already swap per scheme are used directly. **`.check-ok` and `.check-fail` read `--pico-ins-color` / `--pico-del-color` with the same fallbacks the existing rules use.**
5. Every app-owned colour carries a measured ratio for both schemes. **Table above.**

Each row carries a distinct glyph (`✓` / `!` / `✗` / `·`), a bold name, and an `.sr-only` state word (`OK:` / `Warning:` / `Failed:`) before the name. A colour-blind or monochrome reader loses nothing (WCAG 1.4.1).
