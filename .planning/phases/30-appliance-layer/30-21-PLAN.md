<decision_record>
## CR-02: the fix approach, and why

The orchestrator delegated this choice. The tension is real: the pre-probe short-circuit is what
makes phase success criterion 2 -- "the status strip stays fast with the scanner host unplugged" --
true on the SANE side, and `sane_get_devices` is a blocking C call with no timeout at any layer, so
removing the short-circuit can cost ~127 s (Linux retries a SYN six times).

**Rejected: "probe degrades cost only" (always call `get_devices()`, drop the short-circuit).**
It produces a correct verdict with the smallest diff, but it does not merely regress criterion 2's
page latency -- that latency is owned by D-04's cache and background refresher, not by the probe
("a background refresh thread keeps the cache warm; the page always renders from cache … This is
what makes success criterion 2 true. Per-check timeouts are still expected as a second line of
defence, but they are not the mechanism"). What it actually regresses is worse: the refresher tick
holds `worker.scanner_gate` across `run_checks`, so a ~127 s enumeration parks
`ScanWorker._scan_job` behind it with the job row already written `SCANNING` (WR-03). That turns a
display defect into a scan-starvation defect. It would also make `saneless doctor` take two minutes
on exactly the appliance whose operator is running it to find out what is wrong.

**Rejected: "bound the enumeration" (run `get_devices()` on a worker thread with a deadline).**
This is the better answer in a codebase where the call can be abandoned. Here it cannot:
`sane_get_devices` is inside libsane and nothing can interrupt it, so a helper thread that misses
its deadline is *still inside SANE* after the caller has returned and released the gate. That
breaks the single invariant `scanner_gate` exists to hold -- one caller inside libsane at a time
(Pitfall 2) -- and defeats Amendment A-7's shutdown rule, because `scanner.close()` then runs
`sane_exit()` with a SANE call outstanding, which `sane_backend.shutdown()` documents as a segfault
risk. Making it safe means the helper must own the gate itself *and* be visible to
`refresher.stop()`, i.e. a second thread lifecycle added in a gap-closure phase. And the net
portion cannot be skipped selectively instead: the sane-net backend reads `SANE_NET_HOSTS` at
`sane_init` and never again (`sane_backend.py:834-837`), so there is no per-call way to enumerate
locals only.

**Chosen: downgrade the verdict, keep the bound.** The pre-probe keeps its short-circuit -- so the
2 s bound and criterion 2 are untouched, and no thread, deadline or shutdown machinery is added --
but it stops claiming a fact it cannot know. What the probe observed is *"the configured scanner
host did not answer"*, and that is precisely D-01's definition of amber: "a true statement about a
deployment that still works". It is the same shape as D-22's read-only-config row, which set the
amber precedent for exactly this class of fact. `CheckState`'s docstring rule -- a healthy
appliance must never go red -- is then satisfied, because a machine with a working local scanner
and a dead net host reports amber and `doctor` exits 0.

**The cost, recorded deliberately.** An appliance whose *only* scanner is an unreachable net host
now reports amber rather than red, so `doctor` exits 0 for it. That is accepted: D-01 already
states that a scripted gate keys on red only, and the alternative is a red row on a machine that
scans perfectly -- the failure mode `CheckState`'s own docstring forbids outright. The row remains
visible, names the scanner host as the thing that did not answer, and carries the same next step,
so a human loses nothing. A future phase that wants the red back needs the bounded-enumeration
thread, and should read the rejection above before building it.

**Rejected: the review's third suggestion, "gate it on the backend actually being net-only."**
Not buildable with what saneless models today. `ScannerSettings` carries only `host: str`; nothing
in the tree inspects `/etc/sane.d/dll.conf` or otherwise knows whether local backends are enabled,
so there is no data from which to decide "net-only". Implementing it would mean new host
introspection plumbing, which is a larger change than the defect warrants and would itself need a
fallback for the case where the introspection fails. Recorded so a future reader does not have to
re-derive that this option was considered and why it was not taken.

Independently of the choice, and required by the review either way: the probe reads
`os.environ.get("SANE_NET_HOSTS", settings.scanner.host)`, because `_ensure_initialised` honours a
pre-existing env var over `scanner.host` and today's probe can dial a host SANE is not using.
</decision_record>
