<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser DOM -> scan submission | A client can remove a `disabled` attribute and submit anyway |
| paperless token -> rendered reason line | A secret's *state* is reported to a LAN-visible page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-64 | Elevation of privilege | bypassing the disabled button | mitigate | The route guard refuses unconditionally before `create_job`; a raw `TestClient` POST test and plan 30-17's devtools-strip browser test both prove the button is only a courtesy |
| T-30-65 | Information disclosure | the reason line and the rejection message | mitigate | Both are developer constants naming the problem and the file to edit; neither interpolates the token value, the paperless-ngx URL (which may carry `user:pass@`) or exception text. A grep asserts the string lives in Python, not composed in a template |
| T-30-66 | Spoofing (UI) | a status response handing back an enabled button | mitigate | The flag lives in the single button partial that every OOB re-render uses, and a multi-poll test asserts the button stays disabled -- the C-10 regression guard for the new flag |
| T-30-67 | Spoofing (truthfulness) | reusing `WORKER_DEGRADED` | mitigate | A dedicated `RequestRejection` member with its own message; a test asserts the degraded sentence never appears on this path (D-15) |
| T-30-68 | Denial of service | over-generalising to "any FAIL check" | mitigate | Exactly one condition blocks the button. UI-SPEC S8 states it and the plan repeats it: a scanner that is unreachable or a paperless-ngx that is down does **not** block a submit, because the user is allowed to try and will get a plain-language error with a next step |
| T-30-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing |
</threat_model>
