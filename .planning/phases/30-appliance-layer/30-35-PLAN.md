<objective>
Stop the strip announcing that the checks have not run while they are visibly running, and make two
decorative tests load-bearing.

Purpose (R3-WR-04): `POLL_ATTEMPT_CAP`'s justification is arithmetic -- "about two and a half times
the worst probe budget a cold start can cost, `PROBE_CONNECT_SECONDS` for saned plus
`PROBE_READ_SECONDS` for Paperless" -- i.e. 7 s against a 20 s window. Three things this same
module documents make that understate the worst case by more than an order of magnitude:
`getaddrinfo` is outside every budget ("an unreachable resolver costs whatever `resolv.conf`
says"); the pre-probe is per configured host; and on the ordinary local-USB deployment there is no
parseable host, no pre-probe at all, and `_scanner_enumeration` calls `get_devices()`, which this
file itself costs at "roughly 127 s for a silently unreachable host".

So a cold start on a wedged scanner reaches the cap at ~20 s with `results is None`, prints "The
checks have not run yet. Press Check again to try now.", and stops asking while the first probe is
still legitimately in flight. Pressing the button collapses into that probe, emits a fresh chain,
and gives up again 20 s later -- so the appliance can say the checks have not run for as long as
they take to run. The settling poll has the same shape: on a probe longer than ~20 s the chain
expires before the store, which is exactly the "Check again visibly does nothing" symptom R2-WR-03
was raised to close.

Purpose (R3-IN-01, R3-IN-02): two tests cannot fail for the properties they are named after.
`test_a_gated_run_returns_what_an_ungated_run_returns` -- named in `_scanner_result`'s docstring as
the replacement for the uniform-dispatch seam the gate split removed, and called in the 30-30
summary "the only guarantee that doctor and the strip agree" -- runs both paths in the one scenario
where the gate is irrelevant. `test_three_resolved_addresses_share_one_budget` asserts
`timeouts[0] <= budget`, `all(t > 0)` and `timeouts == sorted(timeouts, reverse=True)`, all three of
which a per-socket `settimeout(timeout)` implementation satisfies with `[2.0, 2.0, 2.0]`.

Purpose (R3-IN-06): `skip_scanner` is sampled before `run_checks` and the worker sets
`_current_job_id` before `_scan_job` takes the gate, so a real scan starting inside that window
renders the contention row while the freshness line says "Paused during scan". The message is not
false, but the docs describe the busy row as if contention were its only cause.

Output: a poll window that distinguishes "we gave up" from "we are still waiting", two tests that
fail for their own properties, and documentation that admits the race.

## Out of scope

The probe itself is not re-shaped. Plan 30-21's `decision_record` settled that the 2 s saned
pre-probe short-circuit stays with its FAIL -> WARN verdict, and rejected bounding the enumeration
with a worker thread plus a deadline because `sane_get_devices` is an uninterruptible C call: a
helper thread that misses its deadline is still inside SANE after the caller releases the gate,
which breaks the one invariant `scanner_gate` exists to hold and defeats the shutdown rule that
`scanner.close()` runs `sane_exit()` with no call outstanding. This plan therefore reshapes the
*window*, never the probe.
</objective>

<decision_record>
## Which bound is authoritative: the window follows the probe, under its own cap

R3-WR-04 offers two directions -- raise the cap so the window exceeds the real worst case, or keep
ten attempts and distinguish the two endings. This plan does both, in the only combination that
keeps IN-07's guarantee intact.

Raising `POLL_ATTEMPT_CAP` alone is wrong: the cap exists because an appliance whose refresher
thread has died leaves every open tab asking forever, and a cap sized for a 127 s enumeration would
make a dead-refresher tab ask for minutes on every page load. That cost lands on the healthy-idle
case, which is the common one.

Distinguishing the endings alone is not enough either: a chain that stops asking at 20 s while a
probe is running still never collects that probe's result, whatever sentence it prints.

So: `POLL_ATTEMPT_CAP` keeps its value and its meaning -- "nothing is in flight and nothing has
arrived, stop asking" -- and a second, larger `POLL_PROBE_ATTEMPT_CAP` applies only while
`probe_in_flight` is true, i.e. only while a checker demonstrably holds the single-flight lock.
That second cap is still a cap, so a refresher that died *holding* the lock does not produce an
unbounded poll; it just takes longer to go quiet. And the give-up line is only printed when the
chain ended with nothing in flight, because "press Check again" is useless advice while the thing
the button starts is already running.

**Rejected: let `probe_in_flight` extend the chain with no cap at all.** It reintroduces IN-07's
unbounded poll through a narrower door: `Lock.locked()` stays true forever if the holder dies, and
a thread that dies inside the lock is precisely the failure mode this whole area keeps hitting.
</decision_record>
