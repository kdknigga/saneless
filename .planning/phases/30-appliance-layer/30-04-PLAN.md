for manual duplex, real mutual exclusion on the scanner, and a truthful record of what happened to
the generated profiles at startup.

D-08's "skip the scanner while a scan runs" is a correctness requirement because nothing in
`sane_backend.py` mutually excludes two SANE calls, and D-22's amber row cannot be truthful
without A-2's recorded outcome.
Output: `pass_count_callback`, `ScanWorker.front_pages`, `ScanWorker.scanner_gate`,
`ScanWorker.profile_storage`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| background refresher thread -> SANE control wire | A second thread may enter libsane while a scan is running |
| pipeline observer callbacks -> worker state | A callback raising must not be able to fail a scan |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-13 | Denial of service | two concurrent SANE calls on one control wire | mitigate | `scanner_gate` gives real mutual exclusion; the refresher acquires non-blocking and skips (D-08). The advisory `current_job_id` read alone has a real race (RESEARCH § 1) and is not relied on |
| T-30-14 | Denial of service | a raising `pass_count_callback` aborting a scan | mitigate | The callback is guarded exactly as `thumbnail_callback` is; a test asserts a raising observer still yields a `ScanResult` |
| T-30-15 | Tampering | `front_pages` read across threads | mitigate | Guarded by its own `threading.Lock`, following the `_profiles_lock` precedent; cleared in `_process_job`'s `finally` so no job can read another job's count |
| T-30-16 | Information disclosure | `profile_storage` | mitigate | It is a three-member enum, not a path; the strip's row copy deliberately omits the config path because it is a host filesystem path on a LAN-visible page (UI-SPEC S1) |
| T-30-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing |
</threat_model>
