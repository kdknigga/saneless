<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process shutdown -> live background threads | Resources may be closed while another thread is using them |
| app.state -> every route | The injection channel for the cache and the refresher |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-36 | Denial of service (crash) | `scanner.close()` under a live refresher inside `sane_get_devices` | mitigate | A-7: nothing closes until both threads confirm they stopped; otherwise the lifespan logs and returns, leaving everything open for process exit, exactly as the worker branch already does (D-09, D-18, Pitfall 1) |
| T-30-37 | Denial of service | shutdown taking 2x the bounded join | mitigate | Both stop events are set before either join, so the joins overlap; a test asserts the ordering rather than the timing |
| T-30-38 | Denial of service | a probe delaying server start | mitigate | The refresher starts cold and `_tick` returns immediately with no watcher stamped; a spy asserts zero `run_checks` calls across an empty lifespan (D-04, D-06) |
| T-30-39 | Tampering (XSS) | new Jinja filters returning markup | mitigate | Every filter returns plain text and none is registered as a Markup-producing filter, so Jinja autoescape applies. No `\|safe` is introduced anywhere |
| T-30-40 | Information disclosure | `app.state.checks` reachable from any route | accept | It holds only developer-constant `CheckResult` rows and timestamps, already guarded by plan 30-06's message-safety test |
| T-30-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing |
</threat_model>
