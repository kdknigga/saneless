<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| query parameter `profile` -> worker profile lookup | A client-supplied name selects server-side data |
| config-supplied profile text -> rendered HTML | Operator-written free text crosses into the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-69 | Tampering (path traversal) | the `profile` parameter | mitigate | It is a query parameter looked up against the known profile set via `worker.get_profile` under the profiles lock, answering 422 on a miss -- the same shape `start_scan` already uses (`routes.py:408-411`). It never builds a path, a URL or a template name |
| T-30-70 | Tampering (XSS) | `label` and `description` rendered into `<option>` text and the `<small>` | mitigate | Jinja autoescape is on and no `\|safe` is used; both fields are bounded by `max_length` (plan 30-02); a `<script>`-containing description test asserts the escaped output |
| T-30-71 | Information disclosure | the description route enumerating profile names | accept | Profile names are already rendered in the select on `GET /`, which is unauthenticated by the trusted-LAN decision; the route exposes nothing new |
| T-30-72 | Denial of service | one `get_profile` lock acquisition per profile per render | accept | The profile set is small (one per device source) and each lookup is a dict read under a short lock; the alternative -- a single bulk accessor -- would mean touching `worker.py` in a late wave for no measured benefit |
| T-30-73 | Spoofing (UI) | a blank option after an upgrade | mitigate | `label or name` (Amendment A-3) plus a test with an empty-label profile |
| T-30-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing |
</threat_model>
