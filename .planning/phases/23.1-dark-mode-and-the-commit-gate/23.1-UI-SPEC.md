# Phase 23.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This is a defect fix on an existing UI, not new screens. Only **DARK-01, DARK-02 and DARK-03** have a UI surface. GATE-01/02/03 (commit gate, pre-commit, type-check gating, pyrefly path discipline) are tooling-only, have no UI, and are out of this contract's scope.

**Everything not named here is inherited unchanged** from the master contract `.planning/UI-SPEC.md`: layout, components, spacing, typography, copy, htmx wiring. This phase changes exactly three files in `src/` (`base.html`, `app.css`, `tests/test_browser.py`) plus the master UI-SPEC.

**Evidence base.** Every number below was **measured, not estimated**, on 2026-09-11:
- Pico build: `https://cdn.jsdelivr.net/npm/@picocss/pico@2/css/pico.min.css` resolves to **v2.1.1** (`x-jsd-version: 2.1.1`). Tokens were extracted from that file.
- Computed colours were read by **Chromium 145.0.7632.6** (the repo's Playwright browser) via `getComputedStyle`, under `page.emulate_media(color_scheme=...)`, with the proposed `app.css` applied.
- Contrast ratios use the WCAG 2.x relative-luminance formula, applied to the **rounded `rgb()` strings Chromium returns**, which are the same strings the tests will read.

## Theme Engagement Contract (DARK-01)

### The defect

`src/saneless/web/templates/base.html:2` reads `<html lang="en" data-theme="auto">`. Pico v2.1.1 has **no `auto` value**. Its three theme blocks are:

| Pico v2.1.1 selector | Applies when |
|---|---|
| `:host(:not([data-theme=dark])),:root:not([data-theme=dark]),[data-theme=light]` | Light tokens. Matches `data-theme="auto"`, because `auto` is not `dark` |
| `@media only screen and (prefers-color-scheme:dark){:host(:not([data-theme])),:root:not([data-theme])}` | Dark tokens, automatic. The **only** dark media block in the file. Requires the attribute to be **absent** |
| `[data-theme=dark]` | Dark tokens, forced |

Measured: with `data-theme="auto"` and an emulated dark OS, the root background is `rgb(255, 255, 255)` and the root `color-scheme` is `light`. The app has rendered light for every user since Phase 12.

### Rules

1. **Delete the `data-theme` attribute from `<html>`.** Line 2 of `base.html` becomes exactly `<html lang="en">`. Do not replace it with `"light"`, `"dark"`, or a JS-set value.
2. **Add `<meta name="color-scheme" content="light dark">`** in `<head>`, directly after the viewport `<meta>`. This lets the browser paint a dark canvas and dark native controls *before* the CDN stylesheet arrives, so a dark-preference user does not see a white flash on load. Pico's own `color-scheme` declaration on `:root` still wins once the stylesheet loads.
3. **Pin the Pico URL to the exact build the reference values came from:** `https://cdn.jsdelivr.net/npm/@picocss/pico@2.1.1/css/pico.min.css`. The DARK-01 test asserts Pico's exact surface colour, and `@2` floats. A future 2.x release that shifts the dark surface would fail the test with no change in this repo. Adding SRI is **not** in scope; ROBU-09 (Phase 26) owns that.
4. **No theme toggle, no `app.js` code, no `matchMedia` listener.** The OS preference is the only input. A live OS switch is picked up by the media query with no reload.
5. **Print stays light.** Pico scopes dark to `only screen`, and this app's overrides mirror that.

### Reference surface values (Pico v2.1.1, Chromium-computed)

These are the strings the tests assert. **The page surface lives on `<html>`, not `<body>`.**

| Element | Light | Dark (automatic) | Pico source token |
|---|---|---|---|
| `html` background (**page surface**) | `rgb(255, 255, 255)` | `rgb(19, 23, 31)` | `--pico-background-color`: `#fff` / `rgb(19, 22.5, 30.5)`; Chromium rounds the fractional channels |
| `html` `color-scheme` | `light` | `dark` | set by Pico on `:root` |
| `html` text colour | `rgb(55, 60, 68)` | `rgb(194, 199, 208)` | `--pico-color`: `#373c44` / `#c2c7d0` |
| `body` background | `rgba(0, 0, 0, 0)` | `rgba(0, 0, 0, 0)` | transparent. Pico paints `:root`, **never read this** |
| `article` background (card) | `rgb(255, 255, 255)` | `rgb(24, 28, 37)` | `--pico-card-background-color`: `var(--pico-background-color)` / `#181c25` |
| `td` background (history cells) | `rgb(255, 255, 255)` | `rgb(19, 23, 31)` | `td,th{background-color:var(--pico-background-color)}`, the page surface even inside the card |

> **Correction to ROADMAP success criterion 1.** It says "`body`'s computed background is Pico's dark surface". Measured: `body` is transparent in both schemes, so a test written that way cannot pass even after the fix. The test must read **`document.documentElement`**. The planner should treat criterion 1 as "the root element's computed background". The intent is unchanged.

## Status Colour Contract (DARK-02)

### Measured contrast, after this phase's change

Surfaces the status text actually sits on: `#status-area` paragraphs sit on the **page surface** (`body`, `main` and `#status-area` are all transparent). History status cells sit on the **`td` background**, which equals the page surface. The card surface is listed as a safety margin for any future placement inside an `<article>`.

| Class | Scheme | Computed colour | vs page / `td` | vs card | AA 4.5:1 |
|---|---|---|---|---|---|
| `.status-done` | light | `rgb(29, 106, 84)` | **6.48:1** | 6.48:1 | PASS |
| `.status-error` | light | `rgb(136, 57, 53)` | **7.83:1** | 7.83:1 | PASS |
| `.status-fallback` | light | `rgb(161, 98, 7)` = `#a16207` | **4.92:1** | 4.92:1 | PASS |
| `.status-done` | dark | `rgb(98, 175, 154)` | **6.94:1** | 6.59:1 | PASS |
| `.status-error` | dark | `rgb(206, 126, 123)` | **5.89:1** | 5.60:1 | PASS |
| `.status-fallback` | dark | `rgb(202, 138, 4)` = `#ca8a04` | **6.11:1** | 5.80:1 | PASS |

For the record, before this phase: `#a16207` on the dark page surface is **3.65:1**, and 3.46:1 on the dark card. That confirms the "~3.6:1" in deferred-items.md and is a FAIL.

### Decisions

- **`.status-done` and `.status-error` get no override.** Pico's `--pico-ins-color` and `--pico-del-color` already swap per scheme and pass in both. Keep `color: var(--pico-ins-color, green)` and `color: var(--pico-del-color, red)` byte-for-byte.
- **`.status-fallback` light stays `#a16207`.** It is what users have seen since Phase 23, and it passes at 4.92:1. Changing it is not required.
- **`.status-fallback` dark is `#ca8a04`** (6.11:1). This is the lighter step of the same yellow/amber family as `#a16207` (Tailwind yellow-600 beside yellow-700), so the colour reads as "the same amber, adjusted" rather than a new hue. It deliberately sits **between** the dark ins green (6.94) and dark del red (5.89), so a degraded success never shouts louder than a failure.
- Rejected: `#eab308` (9.36:1). It passes, but it glares brighter than the error red in dark, which inverts the severity hierarchy. Also rejected: Pico `amber-350` `#c79400` (6.55:1). It passes, but it is a different palette family from the light value and would be the app's only Pico-palette literal.
- **The three status colours must stay pairwise distinct** in each scheme. They are, and the existing `test_fallback_colour_differs_from_done_and_error` keeps guarding it.

### CSS contract: the first dark-scheme override in `app.css`

Replace the current `.status-fallback` rule and its comment with exactly this structure (comment wording may vary, but it must explain the *reason* in plain words and must not cite planning artefacts, per SWP-07):

```css
/* Consume-directory fallback: a degraded success, so amber -- deliberately
   neither the done green nor the error red. Pico has no amber among its
   semantic tokens, so the app owns this one, with a light and a dark value.
   The dark selectors mirror Pico v2's own: automatic dark applies only when
   <html> carries no data-theme attribute, and forced dark uses
   data-theme="dark". */
:root {
    --saneless-status-fallback: #a16207;
}

@media only screen and (prefers-color-scheme: dark) {
    :root:not([data-theme]) {
        --saneless-status-fallback: #ca8a04;
    }
}

[data-theme="dark"] {
    --saneless-status-fallback: #ca8a04;
}

.status-fallback {
    color: var(--saneless-status-fallback);
}
```

**Convention this establishes** (it must be copied into `.planning/UI-SPEC.md`):
1. A scheme-dependent colour the app owns is an **app-namespaced custom property** (`--saneless-*`), declared on `:root` with its light value.
2. Its dark value is declared **twice**, with selectors that mirror Pico v2's exactly: `@media only screen and (prefers-color-scheme: dark) { :root:not([data-theme]) }` and `[data-theme="dark"]`. The forced-dark block costs three lines and stops a future toggle from painting light amber on a dark surface.
3. Consuming rules read only the custom property (`color: var(--saneless-status-fallback)`), never a hex.
4. Pico semantic tokens that already swap per scheme are used directly and never overridden.
5. Every app-owned colour carries a measured contrast ratio for both schemes in the master UI-SPEC.

## Palette File Decision (DARK-03)

**Decision: `pico.colors.css` is not linked, not vendored, and not shipped.** Phase 26 (ROBU-09) vendors `pico.min.css` only.

Reasons, all measured:
1. **The existing `var()` name was wrong, so linking would not have been a no-op.** `app.css` reads `var(--pico-color-amber-600, #a16207)`. deferred-items.md and the Phase 23 ICM notes both say linking the palette "would make the token resolve with no CSS change". It would not. Pico v2.1.1's `--pico-color-amber-600` is **`#785800`**, not `#a16207` (which is Tailwind yellow-700). Linking would silently have changed the light colour to `#785800` and given **2.74:1** in dark, a worse failure than today's.
2. The palette file is **73.2 KB** (minified) on every page load, to resolve one token the app now owns outright.
3. It adds one more asset for ROBU-09 to vendor, pin and hash, for no rendered benefit.

Consequence: after this phase `app.css` contains **no `--pico-color-*` reference at all.** The planner should include a grep assertion that `--pico-color-` does not occur in `src/saneless/web/static/app.css`.

### Coupling contract for Phase 26 (ROBU-09)

Phase 26 must, when it vendors Pico:
- vendor **`pico.min.css` v2.1.1** (or re-measure every value in this spec against the new build and update the tests together),
- **not** vendor `pico.colors.css`,
- **not** reintroduce any `data-theme` attribute on `<html>`,
- keep the `--saneless-status-fallback` block intact,
- move the DARK-01/DARK-02 browser tests into CI once assets are local. Today they are `@pytest.mark.browser` and CI runs `-m "not browser"`, so they need CDN egress and run locally only.

## Verification Contract (Playwright computed-colour tests)

All new tests go in `tests/test_browser.py`, marked `@pytest.mark.browser`, and reuse the session-scoped `browser_server` fixture. The existing `TestFallbackStatusRendering._goto` pattern (`page.emulate_media(color_scheme=scheme)` *before* `page.goto`) is the required way to set the scheme. What is genuinely uncertain here is **this app's cascade** (the missing attribute, the override selectors, the surfaces), so that is what the tests measure. They do not re-test Pico's internals.

### T1: dark palette engages (DARK-01, ROADMAP criterion 1)

Parametrised `scheme ∈ {light, dark}` on the idle page:
- `getComputedStyle(document.documentElement).backgroundColor` equals `"rgb(255, 255, 255)"` (light) / `"rgb(19, 23, 31)"` (dark).
- `getComputedStyle(document.documentElement).colorScheme` equals `"light"` / `"dark"`.
- **Never** read `body`'s background. It is `rgba(0, 0, 0, 0)` in both schemes.
- Do not assert on the presence or absence of the attribute as the proof. The requirement is a computed outcome. An attribute check may appear only as a secondary diagnostic.

### T2: status contrast ≥ 4.5:1 in both schemes (DARK-02, ROADMAP criterion 2)

Parametrised `scheme ∈ {light, dark}` × `cls ∈ {status-done, status-error, status-fallback}` × `context ∈ {status-area, history-cell}`:
- Build a probe in the **real context**: a `<p class="{cls}">` appended inside `#status-area`, and a `<td class="{cls}">` in a new `<tr>` appended to `#history-body`. Read its computed `color`, then remove it (same probe discipline as the existing `_PROBE_STATUS_COLOURS`).
- Resolve the **effective background**: walk from the probe up through ancestors to the first `backgroundColor` whose alpha is not 0, falling back to `document.documentElement`. Do not hard-code the surface. The `td` resolves to its own background; the `<p>` resolves to `html`.
- Compute the ratio **in Python** with the WCAG formula (sRGB channel linearisation at the 0.04045 threshold, `L = 0.2126R + 0.7152G + 0.0722B`, `(L1+0.05)/(L2+0.05)`). Put it in a small module-level helper that parses `rgb(r, g, b)` / `rgba(r, g, b, a)` strings. Assert `>= 4.5`.
- Additionally assert the exact fallback colour strings, so a palette drift is caught by name: `"rgb(161, 98, 7)"` in light and `"rgb(202, 138, 4)"` in dark.

### T3: forced dark keeps the dark amber

Light emulation, then `document.documentElement.dataset.theme = "dark"`: the `.status-fallback` probe computes to `"rgb(202, 138, 4)"`. This guards the `[data-theme="dark"]` block, which T2 cannot reach.

### Required mutation checks (executor records the observed result in the SUMMARY)

| Mutation | Test that must fail | Observed value that makes it fail (measured) |
|---|---|---|
| Restore `data-theme="auto"` on `<html>` | T1 (dark) | root background `rgb(255, 255, 255)`, `colorScheme` `light` |
| Delete the `@media … :root:not([data-theme])` override | T2 (dark, `status-fallback`) | `#a16207` on `rgb(19, 23, 31)` = 3.65:1 |
| Delete the `[data-theme="dark"]` override | T3 | fallback computes `rgb(161, 98, 7)` |

### Existing tests: unchanged and expected to stay green

`test_pico_css_applied`, `test_fallback_copy_and_class_render`, `test_fallback_colour_differs_from_done_and_error` (both schemes), `test_scan_button_re_enables_after_a_fallback_swap`, `test_fallback_swap_refreshes_the_history_table`. None reads a colour value that this phase changes in light mode. The dark parametrisations now run against the real dark palette for the first time, and they must still pass.
