# Phase 23.1: Code Review Report

**Reviewed:** 2026-09-11
**Depth:** deep

## Summary

Both defects are genuinely closed. The dark-mode cascade is correct: `base.html` now
leaves `<html>` bare so Pico v2's `:root:not([data-theme])` rule can match, the app's
amber is declared with selectors that mirror Pico's own, and a forced `data-theme="light"`
under a dark OS correctly keeps the light amber (the `:root` base rule wins because
neither dark selector can match). The commit gate works as designed: I ran
`prek run --stage pre-push --all-files` and `--stage pre-merge-commit --all-files` and
confirmed that exactly the two "(full)" type checkers fire and no file-modifying hook does.
I ran the Playwright suite — 30 passed in 4.2 s, no flakes on a clean run.

The defects are in the perimeter around that work, not in the cascade itself.

The one blocking problem is that the evidence this phase produced is not wired to any
gate. CI deselects the `browser` marker, there is no browser job, and prek runs no tests
at any stage — so all 24 Playwright assertions that prove DARK-01/02/03 are fixed run only
when a human remembers to run them. Re-adding `data-theme="auto"` to `base.html` tomorrow
would sail through both required checks.

Below that, three verified inconsistencies matter. First, the phase established a rule
("always name paths, or the checker can check nothing") and applied it to only one of the
two checkers: `uv run ty check` is still pathless at merge, at push and in CI. I measured
both tools in a gitignored checkout — **pyrefly fails loudly (exit 1) while ty prints
"All checks passed!" and exits 0 having found nothing**, which is the opposite of what
`CONTRIBUTING.md` tells the reader. Second, the documented local pre-flight
(`uv run prek run`) skips 23 of 25 hooks when nothing is staged, which is exactly the state
you are in "before you push". Third, the new test fixture reaches past `JobStore`'s public
API and its lock into `_conn` on the strength of a comment that phase 23 has already
made false.

Two findings (missing SRI, CDN vendoring) are explicitly out of scope per the phase brief
and are not reported.

## Critical Issues

### CR-01: The tests that prove this phase's fix are not run by any gate

**Severity:** BLOCKER
**File:** `.github/workflows/ci.yml:46`, `tests/test_browser.py:146,192,213,389,521`
**Issue:**
`ci.yml` runs `uv run pytest -m "not browser"` and there is no second job that runs
`-m browser`. prek runs no tests at any stage (confirmed by running every stage). So the
24 browser-marked tests — `TestDarkModeEngagement` and `TestFallbackStatusRendering`, the
only mechanical proof that dark mode engages, that the amber follows the scheme, and that
every status colour clears WCAG AA — never execute on the enforcing boundary.

This is not a theoretical gap. DARK-01 was a one-attribute regression in `base.html`.
Re-adding `data-theme="auto"`, or bumping the CDN pin on line 8, or dropping the
`:root:not([data-theme])` guard from `app.css`, all produce a green `lint` + `test` and
re-open the exact defect this phase exists to close. The 6 non-browser `TestContrastHelper`
tests do run in CI, but they only pin the arithmetic — they never touch a browser and
cannot see the cascade.

The suite is fast (4.22 s locally) and passes cleanly, so the cost of closing this is a
job, not a redesign.

**Fix:**
```yaml
  browser:
    name: browser
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Install SANE development headers
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends libsane-dev
      - uses: astral-sh/setup-uv@20cfd1bf945f4377ade1205e4dbc17946fc9a30d # v10.0.1
      - run: uv sync --locked
      - run: uv run playwright install --with-deps chromium
      - run: uv run pytest -m browser
```
Then add `browser` to the required checks on the `master` ruleset and to the table in
`CONTRIBUTING.md:49-55` (which currently advertises "five checks").

## Warnings

### WR-01: `ty` is still invoked pathless at merge, at push and in CI

**Severity:** WARNING
**File:** `.pre-commit-config.yaml:83`, `.github/workflows/ci.yml:31`
**Issue:**
The phase's stated rule is that a type checker must be given explicit paths or it can be
filtered down to nothing by an ignore file. `pyrefly` got that treatment in all three
places. `ty` did not: `ty-checker-full` runs `uv run ty check` and CI runs the same.

I measured both tools inside a gitignored directory (`.claude/worktrees/_probe_review`,
matched by `.gitignore:314`) holding a file with a deliberate `int`→`str` return error:

| invocation | result |
|---|---|
| `ty check` (pathless) | `All checks passed!`, exit 0 — **error not found** |
| `ty check src` | `Found 1 diagnostic` |
| `pyrefly check` (pathless) | `No Python files matched`, exit 1 |
| `pyrefly check src` | `1 error` |

So the silent-success failure mode the phase set out to eliminate belongs to `ty`, not to
`pyrefly`. In a *real* `git worktree` the ignore walk stops at the worktree's repo boundary
and pathless `ty` does find the error (I verified this separately, including an error
placed in `tests/`), so the current `.claude/worktrees/` workflow is not affected today —
but `ty-checker-full` is the merge/push gate, and a gate with a configuration in which it
reports success having checked zero files should not be left standing when the fix is four
characters. `uv run ty check src tests` was verified to pass cleanly on the current tree.

**Fix:**
```yaml
      - id: ty-checker-full
        name: ty type checker (full)
        entry: uv run ty check src tests
```
and in `.github/workflows/ci.yml:31`:
```yaml
      - run: uv run ty check src tests
```
Update the "Why pyrefly always gets explicit paths" section to cover both checkers.

### WR-02: `CONTRIBUTING.md` states the wrong failure mode for pathless pyrefly

**Severity:** WARNING
**File:** `CONTRIBUTING.md:130-135`
**Issue:**
The section says running pyrefly without paths in a gitignored checkout means "it can
report success having checked nothing." Measured behaviour is the opposite: pyrefly exits
**1** with `No Python files matched patterns ...`. The comment in
`.pre-commit-config.yaml:68-72` gets this right ("the hook fails with 'No Python files
matched'") — so the two documents in this same changeset contradict each other, and the
one a new contributor reads first is the wrong one.

The consequence is not cosmetic: a contributor who believes pyrefly fails silently, and who
knows nothing about `ty`'s actual silent pass (WR-01), will trust the wrong half of the
gate.

**Fix:** Replace the last sentence of that section with the measured behaviour, and name
the tool that really does pass silently:
> In a checkout inside a gitignored directory, running `pyrefly` without paths filters out
> every source file and the command fails loudly with "No Python files matched". `ty` in
> the same position reports "All checks passed!" and exits 0 without checking anything.
> Both are wrong answers; naming the paths is what prevents them.

### WR-03: The documented local pre-flight checks almost nothing

**Severity:** WARNING
**File:** `CONTRIBUTING.md:80-84`, `CLAUDE.md:18`
**Issue:**
`CONTRIBUTING.md` says "The repository ships a hook configuration. Run it before you push:
`uv run prek run`", and `CLAUDE.md:18` annotates the same command as "Run all pre-commit
hooks". Neither is true in the state a contributor is actually in before pushing: work is
committed, so nothing is staged, and prek's default scope is the staged set. Measured on
this tree with nothing staged:

```
check for added large files.....(no files to check)Skipped
... 22 more hooks, all Skipped ...
ty type checker (src)...........Passed
pyrefly type checker (src)......Passed
```

23 of 25 hooks did nothing. A contributor following this instruction gets no ruff lint, no
format check, no `debug-statements`, no `detect-private-key`, and believes the tree is
clean.

**Fix:** Use `uv run prek run --all-files` in both files, and correct the `CLAUDE.md`
comment to "Run all hooks over the whole tree". Keep the bare `prek run` only where the
staged-set scope is the point.

### WR-04: Read-only hooks were silenced at merge and push as collateral

**Severity:** WARNING
**File:** `.pre-commit-config.yaml:5-7`
**Issue:**
`default_stages: [pre-commit]` is justified in the comment by "where a file-modifying hook
would abort the operation". That reasoning covers the nine fixers (`ruff --fix`,
`ruff-format`, `end-of-file-fixer`, `trailing-whitespace`, `mixed-line-ending --fix`,
`fix-byte-order-marker`, `pretty-format-json`, `sort-simple-yaml`, `sync-with-uv`). It does
not cover the ~13 read-only hooks that were swept up with them. Verified by running both
stages: **only** `ty type checker (full)` and `pyrefly type checker (full)` fire at
`pre-merge-commit` and `pre-push`.

The concrete losses: `check-merge-conflict` no longer runs at `pre-merge-commit` — the one
stage named after the operation it guards; `detect-private-key` and `detect-aws-credentials`
no longer run at `pre-push`, the last point before content leaves the machine; and lint and
format are not checked at push at all, so the cheapest, fastest failures in the five-check
gate are deferred to a CI round trip while the two slowest (the type checkers) run locally.
That inversion works against the phase's goal of a meaningful local gate.

**Fix:** Add `stages: [pre-commit, pre-merge-commit, pre-push]` to the read-only upstream
hooks (`check-ast`, `check-merge-conflict`, `check-symlinks`, `check-json`, `check-toml`,
`check-xml`, `check-yaml`, `check-vcs-permalinks`, `debug-statements`,
`detect-aws-credentials`, `detect-private-key`), and add a non-mutating lint pair scoped to
those stages:
```yaml
      - id: ruff-check-full
        name: ruff (no fix)
        entry: uv run ruff check --no-fix .
        language: system
        pass_filenames: false
        always_run: true
        stages: [pre-merge-commit, pre-push]
      - id: ruff-format-check
        name: ruff format --check
        entry: uv run ruff format --check .
        language: system
        pass_filenames: false
        always_run: true
        stages: [pre-merge-commit, pre-push]
```

### WR-05: `test_pico_css_applied` asserts nothing and hides the suite's CDN dependency

**Severity:** WARNING
**File:** `tests/test_browser.py:155-165`
**Issue:**
```python
box = main.first.bounding_box()
assert box is not None
# PicoCSS centers main content -- left margin should be > 0 on wide
# viewports (default 1280px, PicoCSS max-width ~1200px)
```
`bounding_box()` returns a box for any rendered element, styled or not. The assertion holds
with the stylesheet removed entirely, and the stated check (left margin > 0) is written as a
trailing comment with no code behind it — dead intent in the one test whose name claims to
verify that Pico loaded.

This matters more than a usual vacuous test, because every colour assertion in
`TestDarkModeEngagement` and `TestFallbackStatusRendering` silently depends on
`cdn.jsdelivr.net` being reachable during the run. With the CDN unreachable the suite does
not report "Pico did not load"; it reports
`AssertionError: ('rgb(0, 0, 0)', 'rgb(255, 255, 255)', 21.0)` and colour mismatches that
look like a palette regression.

**Fix:** Make this test the load canary:
```python
def test_pico_css_applied(self, page: Page, browser_server_url: str) -> None:
    """PicoCSS is loaded: <main> is centred by Pico's container rule."""
    page.goto(browser_server_url)
    box = page.locator("main").first.bounding_box()
    assert box is not None
    assert box["x"] > 0, f"PicoCSS did not load (main at x={box['x']})"
```
and reference it from the module docstring as the diagnosis for a mass colour failure.

### WR-06: `fallback_page` teardown does not restore the idle state it claims to

**Severity:** WARNING
**File:** `tests/test_browser.py:402-424`, `tests/test_browser.py:534-539`
**Issue:**
The fixture's teardown sets `app.state.worker._current_job_id = None` with the comment
"a job left as 'current' would follow every later test onto the idle page". It does not
achieve that. Both `index()` (`routes.py:82-86`) and `current_job_status()`
(`routes.py:188-192`) fall back to `job_store.list_recent(limit=1)` when
`current_job_id` is `None` — and the most recent job is the FALLBACK job the fixture just
created. The job is never deleted, so the page stays exactly as non-idle as before.

Consequences: `TestDarkModeEngagement._goto`'s docstring ("The idle page renders no status
line") is false for every test in that class as actually run; the seven jobs created across
the parametrised fallback tests accumulate in the session-scoped store, so the history table
grows during the session; and the pass/fail meaning of `test_flip_prompt_not_visible_on_idle`
(line 217) and `test_scan_button_present` (line 230) depends on their position in file
order rather than on any stated precondition.

Nothing fails today, which is precisely why it will rot unnoticed.

**Fix:** Delete the job in teardown rather than only unsetting the pointer, or give the
fixture its own store. Minimal version:
```python
finally:
    app.state.worker._current_job_id = None
    with job_store._lock, job_store._conn:  # or add a public delete_job()
        job_store._conn.execute("DELETE FROM jobs WHERE id = ?", (job.id,))
```
Better: add `JobStore.delete_job(job_id)` (the store has no deletion API outside `prune`)
and correct the `_goto` docstring in `TestDarkModeEngagement`.

### WR-07: The fixture bypasses `JobStore`'s public API and its lock, on a stale premise

**Severity:** WARNING
**File:** `tests/test_browser.py:410-417`
**Issue:**
```python
# No warning writer lands until plan 23-07; the column is written
# directly so the inline warning paragraph has something to render.
with job_store._conn:
    job_store._conn.execute("UPDATE jobs SET warning = ? WHERE id = ?", ...)
```
Two problems. The comment is stale — plan 23-07 landed; `JobStore.finish_job(job_id, state,
result=JobResult(...))` is the public writer for `warning` and the worker already uses it
(`worker.py:265-275`). And the workaround it justifies is unsafe by the store's own
documented rules: every public writer is wrapped in `@_locked` (`job.py:562, 638, 668, 741`)
because the web thread and the worker thread share one connection opened with
`check_same_thread=False`, and the module docstring at `job.py:466-472` warns that sqlite3
connection context managers do not nest — "an inner `with conn:` commits the outer
transaction". This fixture opens `with self._conn:` from the test thread holding no lock, so
it can commit another thread's in-flight transaction. Benign only because no scan runs
during browser tests; it is a pattern that fails the moment one does.

**Fix:**
```python
from saneless.job import JobResult
from saneless.vocabulary import ScanOutcome

job = job_store.create_job(profile="default", title="Fallback Doc")
job_store.finish_job(
    job.id,
    JobState.FALLBACK,
    result=JobResult(
        outcome=ScanOutcome.FALLBACK,
        warning="Title, tags and correspondent were not applied.",
        pages_scanned=1,
        pages_removed=0,
        pages_uploaded=0,
    ),
)
```
This also removes the separate `update_state` call on line 410.

### WR-08: The contrast probe treats any translucent background as opaque

**Severity:** WARNING
**File:** `tests/test_browser.py:291-324`, `tests/test_browser.py:327-334`
**Issue:**
`_PROBE_CONTEXT_CONTRAST` walks up to "the first ancestor that paints one" using an
`isTransparent` test that only recognises alpha exactly `0`. `_relative_luminance` then
discards the alpha channel entirely (`inner.split(",")[:3]`). So a background of
`rgba(111, 120, 135, 0.0375)` — a colour that renders as near-white over a white page — is
measured as solid `#6F7887`.

This is currently unreachable: I confirmed Pico 2.1.1 applies its stripe only via
`table.striped tbody tr:nth-child(odd)`, and `history.html` uses `role="grid"`, which Pico
2.1.1 does not stripe. But the failure is one class attribute away. Adding
`class="striped"` to the history table would turn a genuinely passing ~4.7:1 into a measured
~1.1:1 and fail `test_status_colour_meets_aa_contrast` with a number that is not the number
a user would experience — a false failure that will cost an afternoon to diagnose.

`_relative_luminance` will also raise `ValueError` rather than assert if a browser ever
returns `color(srgb ...)` or a keyword (`.index("(")`).

**Fix:** Composite instead of ignoring alpha. In the JS probe, keep walking while alpha is
`< 1` and blend, or simpler, blend in Python:
```python
def _blend_over(colour: str, backdrop: tuple[float, float, float]) -> str:
    """Composite an rgba() colour over an opaque backdrop."""
```
and treat any `alpha < 1` ancestor as "keep walking, then blend the collected stack over the
root surface". Also raise a clear assertion if the string does not start with `rgb`.

### WR-09: Four hard-coded palette constants with nothing tracking their source

**Severity:** WARNING
**File:** `src/saneless/web/static/app.css:27,32,37`, `tests/test_browser.py:371-373,556,588,604`, `src/saneless/web/templates/base.html:8`
**Issue:**
The fallback amber exists as `#a16207`/`#ca8a04` in two CSS declarations, as
`rgb(161, 98, 7)`/`rgb(202, 138, 4)` in the `amber` dict at line 588 and again at 604, and
as reference ratios pinned to those exact values at lines 371-373. Pico's dark surface is
hard-coded as `rgb(19, 23, 31)` at line 552 and 365. All of it is valid only for
`@picocss/pico@2.1.1`, pinned in `base.html:8`.

Nothing watches that pin: `.github/dependabot.yml` covers `package-ecosystem:
"github-actions"` only, so the CDN version is outside every automated update path. And per
CR-01 the tests that would catch a drift do not run in CI. The exact pin is the right call
given the assertions, but the combination means a future Pico bump is a manual edit whose
breakage surfaces only when a human happens to run `-m browser`.

**Fix:** Fix CR-01 first, so the pin is at least enforced. Then hoist the expectations into
one module-level table in the test file, e.g.
```python
# Valid for @picocss/pico@2.1.1 pinned in base.html.
_PICO_SURFACE = {"light": "rgb(255, 255, 255)", "dark": "rgb(19, 23, 31)"}
_AMBER = {"light": "rgb(161, 98, 7)", "dark": "rgb(202, 138, 4)"}
```
and reference it from all four sites so a bump is a one-line edit with a named reason.

### WR-10: The explicit-stages comment gives the wrong reason, and will mislead the next edit

**Severity:** WARNING
**File:** `.pre-commit-config.yaml:5-6,13,16,29,36`
**Issue:**
The header comment explains the four `stages: [pre-commit]` pins as being about
file-modifying hooks. That is not the mechanism. I read the upstream manifest
(`pre-commit-hooks` v6.0.0) — the pins are needed because those four hooks declare their own
`stages` and a manifest-declared `stages` overrides `default_stages`:

| hook | upstream `stages` | modifies files? |
|---|---|---|
| `check-added-large-files` | `[pre-commit, pre-push, manual]` | no |
| `check-executables-have-shebangs` | `[pre-commit, pre-push, manual]` | no |
| `end-of-file-fixer` | `[pre-commit, pre-push, manual]` | yes |
| `trailing-whitespace` | `[pre-commit, pre-push, manual]` | yes |

Two of the four are read-only, so the stated reason cannot be the real one. The pins
themselves are correct and complete for the current hook list — but the comment teaches the
wrong rule, and the same manifest declares `stages` on `check-shebang-scripts-are-executable`
and `destroyed-symlinks`. Adding either later, guided by this comment, would silently
re-open the merge/push stages to a hook nobody intended to run there.

**Fix:**
```yaml
# default_stages keeps hooks at commit time only. It does NOT override a hook whose own
# manifest declares `stages:` -- pre-commit-hooks v6.0.0 declares
# [pre-commit, pre-push, manual] on check-added-large-files,
# check-executables-have-shebangs, end-of-file-fixer and trailing-whitespace, so each of
# those is pinned explicitly below. Check the upstream manifest before adding a hook.
default_stages: [pre-commit]
```

## Info

### IN-01: `types: [python]` is inert on all four local hooks

**File:** `.pre-commit-config.yaml:64,76,85,94`
**Issue:** With `always_run: true` and `pass_filenames: false`, the hook runs regardless of
which files changed and receives no filenames, so `types` has no effect. It reads as though
the hook is scoped to Python changes, which it is not.
**Fix:** Drop `types: [python]` from the four local hooks, or drop `always_run: true` if
change-scoping was actually intended (it should not be — the checkers take explicit paths).

### IN-02: `sort-simple-yaml` can never run

**File:** `.pre-commit-config.yaml:34`
**Issue:** Upstream declares `files: '^$'` for this hook, a pattern that matches nothing.
The hook has never executed and never will unless the config supplies its own `files:`.
**Fix:** Remove it, or give it an explicit `files:` naming the simple YAML files it should
sort.

### IN-03: The dark amber is written twice with no single source

**File:** `src/saneless/web/static/app.css:32,37`
**Issue:** `#ca8a04` appears in both the `prefers-color-scheme` block and the
`[data-theme="dark"]` block. Plain CSS cannot merge the two selectors, so this duplication
is structural rather than careless — but a palette change requires both edits and only one
is obvious from a grep for `data-theme`.
**Fix:** Leave the selectors as they are and add a one-line comment on the second
declaration pointing at the first, so an edit to one prompts the other.

### IN-04: Nothing prompts existing clones to install the two new git shims

**File:** `.pre-commit-config.yaml:4`, `CONTRIBUTING.md:26-28`
**Issue:** `default_install_hook_types` now lists three hook types, but a clone that ran
`prek install` before this phase has only the `pre-commit` shim. Those checkouts get the
src-only checks at commit and nothing at merge or push, with no warning that the new stages
exist.
**Fix:** Add a line under "Setting up": "If you installed the hooks before phase 23.1,
re-run the install command — it now installs three shims rather than one."

### IN-05: Server teardown ignores whether the thread actually exited

**File:** `tests/test_browser.py:136-137`
**Issue:** `thread.join(timeout=5)` discards its outcome. A uvicorn thread that fails to
stop leaves a bound port and a live app for the rest of the session, reported as nothing.
**Fix:**
```python
server.should_exit = True
thread.join(timeout=5)
assert not thread.is_alive(), "uvicorn test server did not shut down"
```
