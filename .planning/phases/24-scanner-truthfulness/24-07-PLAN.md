<objective>
Give the two facts the backend now measures — the resolution the device actually used, and how many
pages it could not read — a single route out of the scanner, and make the pipeline use them.

Purpose: `scan_pages` yields `Image` only, so neither fact can leave the backend at all. It is a
**generator**, and `list(generator)` discards the generator's return value — measured — and none of
the three pipeline call sites use `yield from`. So D-12 necessarily changes the `ScannerBackend` ABC.
This matters for correctness, not tidiness: Phase 23 made `profile.resolution` authoritative for
`img2pdf.get_fixed_dpi_layout_fun`, so a device that substitutes DPI now produces both a mis-cropped
page and a wrong MediaBox — re-opening part of OUTC-06, which was Phase 23's headline fix.

Output: a minimal frozen `ScanBatch`, an ABC that returns it, 89 updated references, and two
`dpi=profile.resolution` call sites fed from the device instead.

**This is the highest-risk plan in the phase.** Its blast radius was measured at ~2.5x the original
estimate, and the type checkers will not find all of it.
</objective>

The recommended shape (RESEARCH.md Q3), modelled on `pipeline.ScanResult`:

```python
@dataclass(frozen=True)
class ScanBatch:
    """The pages one acquisition produced, and what the device actually did."""
    pages: list[Image.Image]
    actual_resolution: int      # read back from the device (D-11)
    pages_rejected: int         # integrity failures skipped (D-06/D-07)
```

page records. Note `ScanResult`, `DeviceInfo`, `DeviceCapabilities`, `ScanSettings` and
`PipelineRequest` are all **plain** `@dataclass`; there is no `frozen=True` precedent in this
codebase, so state the choice and the reason rather than copying the analog verbatim.

which becomes `Returns:`:
