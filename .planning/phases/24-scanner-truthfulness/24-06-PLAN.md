<objective>
Make the geometry path tell the truth three times over: write geometry only when the device says it
has the options, scale by the unit the descriptor reports rather than assuming millimetres, and
notice when the device silently clamped the area you asked for.

Purpose: `_set_geometry` assumes assigning `dev.tl_x` raises on a device without that option. The real
`SaneDev.__setattr__` stores unknown keys **silently** (verified in the installed `sane.py:188`), so
the function returns `True`, no crop happens, and `paper_size` is silently ignored (M-15). It also
writes `br_x = 210.0` assuming millimetres though the unit lives at option-tuple index 5 (N-03). And
research measured a third failure of the same shape: writing A4's 210 mm to a device whose `br_x`
range is `(0.0, 200.0, 1.0)` clamps to 200.0 with no error and no exception, so `_set_geometry` can
return `True` having set an area that is not the one requested (D-19).

Output: presence-checked geometry, a total `GeometryUnit` enum, area read-back, and a crop fallback
that is finally reachable — proven by a test against a fake that behaves like the real library.
</objective>

The complete SANE unit set, re-confirmed directly from `_sane` (not from `sane.UNIT_STR`, which is a
display dict for `Option.__repr__`):

```
UNIT_NONE = 0
UNIT_PIXEL = 1
UNIT_BIT = 2
UNIT_MM = 3
UNIT_DPI = 4
UNIT_PERCENT = 5
UNIT_MICROSECOND = 6
```

**There is no `UNIT_CM` and no `UNIT_INCH`.** A backend cannot report either. Do not add those
branches. (User-facing scan-area units in cm and inches are a Deferred Idea with its own future
phase; nothing here implements them.)

Measured on real `test:0` (RESEARCH.md § Finding 8): `tl-x`/`br-x` report `type=2` (`TYPE_FIXED`),
`unit=3` (`UNIT_MM`), constraint `(0.0, 200.0, 1.0)`. Writing `br_x = 210.0`, `br_y = 297.0` and
reading `dev.area` back gives `((0.0, 0.0), (200.0, 200.0))` — clamped, silently.

The hyphen/underscore asymmetry, measured. `get_options()` reports **hyphens**; attribute assignment
uses **underscores**. Both spellings are load-bearing and a single set of constants used for both will
be wrong on one side:

```
OPT (24, 'tl-x', 'Top-left x', ..., type=2, unit=3, size=4, cap=5, (0.0, 200.0, 1.0))
dev.tl_x = 0.0
```

The house pattern for a total lookup, from `src/saneless/scanner/base.py:43-50` — a `match` with
`assert_never`, **never** a `dict`. Phase 21's D-08 measured that a `dict[Enum, str]` missing a member
draws no diagnostic from either `ty` or `pyrefly`, while the same enum in a `match` is caught by both,
at edit time. Copy the reasoning paragraph at `src/saneless/vocabulary.py:245-249` into
`GeometryUnit`'s docstring rather than re-deriving it.

Note on the enum base: every enum in this codebase is a `StrEnum`. `GeometryUnit` maps **integer**
SANE codes, so it is the project's first integer-valued member set. There is no in-repo analog for
that half; only the `match`/`assert_never` half transfers.
