## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pipeline thread -> job database | The worker thread writes terminal state while the web request thread reads it. `JobStore`'s `RLock` is the only serialisation. |
| exception text -> `job.error` column | `str(exc)` from an arbitrary pipeline exception is persisted and later rendered. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-33 | Repudiation | the unconditional `JobState.DONE` write at `worker.py:250` | mitigate | This is C-03 itself: the job record claims a success that may not have happened, and the audit trail the user relies on is a lie. The control is structural rather than defensive — the terminal state is now *derived* from the outcome the pipeline returned, through a total `match` with `assert_never`, so there is no code path that writes DONE without an outcome that maps to it. An inline `if/else` was rejected for exactly this reason (D-02). |
| T-23-34 | Tampering | concurrent writes to the same job row | mitigate | `finish_job` carries `@_locked`, enforced by `TestLockDiscipline`'s reflective test, which has no opt-out list. It also opens its own `with self._conn:` and calls no other public method — the AST test enforces that, because sqlite3 context managers do not nest and an inner `with conn:` would commit the outer transaction, landing half the caller's work early. A concurrency test extends Phase 22's STOR-01 property to the new method. |
| T-23-35 | Tampering | `update_state` blanking the result columns on every in-flight transition | mitigate | `update_state`'s SQL is an unconditional `SET state, error, error_category`. Extending it with six more columns — the obvious-looking change — would blank the results on every `SCANNING` / `ASSEMBLING` / `UPLOADING` write. D-04 forbids it and the acceptance criteria require `git diff` to show no change inside `update_state`. |
| T-23-36 | Repudiation | writing `0` page counts on the failure path | mitigate | Phase 22's D-08 defines `NULL` as "never recorded" and a measured zero as `0`. A job that failed before the scanner opened has not measured zero pages, and recording `0` would make the two indistinguishable forever. `finish_job`'s failure call passes no `result`, and a test asserts all three columns read back as `None`. |
| T-23-37 | Information Disclosure | `str(exc)` from an arbitrary exception persisted into `job.error` | mitigate | The upstream half is bounded by plan 23-04's 500-character cap on any interpolated paperless response body, and the preservation path in plan 23-06 adds only a local filesystem path. Rendering is escaped, proven by plan 23-05's XSS regression test. This plan adds no new interpolation of its own — it persists what the exception already said. |
