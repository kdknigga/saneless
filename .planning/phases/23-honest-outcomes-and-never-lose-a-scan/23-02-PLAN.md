<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator env / TOML -> saneless | `SANELESS_OUTPUT__DATA_DIR` and `output.data_dir` are operator-controlled paths that become filesystem write destinations for the job database and every preserved scan. |
| container image -> host volume | The image bakes a path the compose file must agree with. Disagreement silently writes durable data into an ephemeral layer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-04 | Denial of Service | `data_dir` unwritable at preservation time | mitigate | The `data_dir` writability block added to `validate_settings_dirs` fails at startup with `ConfigError`, not mid-scan. Discovering an unwritable `failed/` at the moment a scan needs preserving is the worst possible time — that is the entire reason D-16 puts the check beside the existing `tmp_dir` and `consume_dir` ones. Verified by the unwritable-`data_dir` test with a `chmod(0o444)` directory. |
| T-23-05 | Denial of Service | `sqlite3.connect` into a missing `data_dir` | mitigate | RESEARCH Pitfall 3 verified by execution that `sqlite3.connect` raises `OperationalError: unable to open database file` rather than creating parents. Both entry points mkdir `data_dir` before constructing `JobStore`; the clean-machine `HOME=$(mktemp -d) uv run saneless jobs` smoke test is the acceptance control. |
| T-23-06 | Tampering | `data_dir` as an env-controlled write root | accept | `SANELESS_OUTPUT__DATA_DIR` is operator-controlled configuration, not attacker-controlled input, and it sits at the same trust level as `tmp_dir`, `consume_dir` and `log_file`, which have been env-settable since Phase 1. No new privilege is granted. The genuinely new attack surface in this phase is the user-supplied *job title* becoming part of a path — that is T-23-07 in plan 23-03, where the allow-list sanitiser lives. |
| T-23-07 | Information Disclosure | preserved scans in the container writable layer | mitigate | Without D-15's `ENV`, `failed_dir` resolves to `/root/.local/state/saneless/failed` inside the image — covered by no volume, destroyed on recreation, and included in any image commit or export. The baked `ENV` plus the `VOLUME` declaration means a preserved scan is never written into a layer that can be pushed to a registry. |
| T-23-08 | Repudiation | orphaned `saneless.db` in the old volume root | accept | D-14 locks "no migration": after the compose repoint, the `saneless-data` volume still holds the old `saneless.db` at its root. Job history is prunable ephemera (7 days / 500 rows by default), the documents themselves are in paperless, and a startup filesystem mutation can fail in a container with an unwritable old path. Mitigation is documentation, owned by plan 23-09's upgrade note. |
</threat_model>
