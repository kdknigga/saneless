<objective>
Stop the temporary directory from destroying a finished scan when delivery fails, and make the
duplex-mismatch path as honest as the simplex one.

Purpose: OUTC-04 (D-06, D-07, D-10), OUTC-03 (D-08), and the preservation half of OUTC-01. This is
the plan the phase is named after: `pipeline.py:448` wraps the whole run in a `TemporaryDirectory`,
so any raise after assembly unwinds it and deletes the PDF. Plan 23-04 made `poll_task` raise; until
this plan lands, that raise loses documents.

Output: one preservation guard, spanning `upload_document` **and** `poll_task`, used by both
delivery paths, moving every assembled PDF to `<data_dir>/failed/` and re-raising with the
destination named.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `tmp_dir` -> `<data_dir>/failed/` | A file crosses from ephemeral scratch space into durable, operator-visible storage, possibly across a filesystem boundary. The destination basename is derived from a user-supplied job title. |
| delivery exception -> `job.error` | The message this plan constructs is written to the job row and rendered in the web status area, so it is a user-facing string built from an upstream exception plus a local filesystem path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-26 | Tampering | `failed_dir / pdf_path.name` written from a user-supplied title | mitigate | The basename comes from plan 23-03's `build_pdf_filename`, whose `[a-z0-9]` allow-list sanitiser removes `/`, `\`, `.` and NUL by construction, so the join cannot escape `failed_dir`. This plan adds no second sanitisation point — one sanitiser with one set of tests is the control, and duplicating it would create a second place to get it wrong. |
| T-23-27 | Tampering | `shutil.move` onto a directory raising `shutil.Error` inside an exception handler | mitigate | Verified in RESEARCH: `shutil.move(src, existing_dir)` raises `shutil.Error` — which does not inherit from `OSError` — on basename collision, so it would escape an `except OSError` handler and mask the original delivery failure. Control: always pass the explicit full destination path, whose branch goes straight to `os.rename`. Regression test: run the same failing delivery twice and assert two files survive. |
| T-23-28 | Denial of Service | cross-device move failing with EXDEV | mitigate | `data_dir` and `tmp_dir` are now independent settings and can be on different filesystems, where `os.replace` raises `OSError: [Errno 18] Invalid cross-device link` (verified by execution). `shutil.move` falls back to copy-then-unlink. D-06 mandates it by name; the acceptance criteria assert `os.replace` and `.rename(` appear nowhere in `pipeline.py`. |
| T-23-29 | Denial of Service | unbounded growth of `<data_dir>/failed/` | accept | Nothing prunes `failed/`, and every unrecoverable delivery adds a PDF. **Accepted deliberately, not overlooked.** Pruning preserved scans is precisely the data loss this phase exists to prevent, and an automatic sweep would need a retention policy, a config key and a user story that do not exist yet. The bound in practice is operator attention: every preserved file corresponds to a job the UI shows as failed with that path in its error message, so the directory cannot fill silently. Mitigation is documentation — plan 23-09 must tell operators that `failed/` is theirs to drain and that paperless-ngx detects re-ingested duplicates by checksum. Revisit if a retention requirement appears in a later milestone. |
| T-23-30 | Information Disclosure | the preservation path and upstream error text in `job.error` | mitigate | The re-raised message concatenates `str(exc)` and an absolute path. The upstream half is already bounded by plan 23-04's 500-character cap on any interpolated paperless response body. The path half discloses the operator's own `data_dir` to the operator's own single-user LAN UI, which is the point — OUTC-04 requires the job error to name the file so the user can find it. Rendering is escaped, proven by plan 23-05's XSS regression test. |
| T-23-31 | Repudiation | a preservation failure silently masking the delivery failure | mitigate | If the move itself raises, the handler builds a message naming BOTH failures and chains `from exc`. A user who is told only "upload failed" while the scan was also destroyed has been actively misinformed. Covered by a dedicated test with an unwritable `failed_dir`. |
| T-23-32 | Elevation of Privilege | `except Exception` swallowing an interrupt | mitigate | `KeyboardInterrupt` and `SystemExit` derive from `BaseException`, not `Exception`, so they propagate untouched and no shutdown path is captured. The guard also always re-raises, so nothing is swallowed even for the types it does catch — it only adds a side effect and a message. |

**Package changes in this plan:** none.
