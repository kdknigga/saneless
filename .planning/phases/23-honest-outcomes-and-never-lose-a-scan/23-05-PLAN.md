<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| job database -> rendered HTML | `job.title`, `job.error` and the new `job.warning` are rendered into the status partial and the history table. `title` is user-supplied; `error` and `warning` can carry text originating from paperless-ngx (see plan 23-04's T-23-16). |
| job database -> terminal output | `saneless jobs` writes the same fields to a TTY, where control sequences rather than markup are the injection vector. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-21 | Tampering | `{{ job.warning }}` and `{{ job.error }}` rendered in `status.html` | mitigate | FastAPI's `Jinja2Templates` enables autoescaping by default, but this plan adds a NEW interpolation of a field whose content can originate upstream of saneless, so the property gets an explicit regression test rather than an assumption: Task 1 drives a job to FALLBACK with a warning containing `<script>alert(1)</script>` and asserts the raw tag does not appear in the response while the escaped form does. If that test fails, autoescaping is off and the fix is to turn it on, never to sanitise at the call site. |
| T-23-22 | Denial of Service | an unbounded `warning` or `error` string flooding the status area | mitigate | Upstream control: plan 23-04 Task 1 caps the interpolated paperless response body at 500 characters before it ever reaches the `error` column. This plan's contribution is to render the warning in its own `<p>` rather than concatenating it into the title line, so a long value wraps in its own block instead of destroying the status-area layout. |
| T-23-23 | Repudiation | the Scan button staying permanently disabled after a fallback | mitigate | `.planning/UI-SPEC.md:286` predicted this exactly: `app.js` re-enables only on `.status-done` or `.status-error`. Leaving it would make a *successful-but-degraded* scan look like a locked-up application — a worse user-facing failure than the silent DONE this phase removes. Control: the class is added to the condition, and the fix is verified through a real browser (Playwright asserting `#scan-btn` is not disabled), not through a grep, because a grep cannot prove the handler actually fires. |
| T-23-24 | Repudiation | a stale history table after a fallback | mitigate | `.planning/UI-SPEC.md:281` documents the hidden `hx-trigger="load"` reload as firing on terminal DONE/ERROR. FALLBACK is terminal (D-03), so the same div is copied into the new branch, and a dedicated test asserts its presence for FALLBACK and its absence for a non-terminal state. |
| T-23-25 | Tampering | terminal control sequences in `saneless jobs` output | accept | `j.title` is echoed through `click.echo` and could in principle carry ANSI escapes. The risk is unchanged by this plan — titles have been echoed since Phase 1 — and the writer and the reader are the same single local user of a LAN appliance. Recorded so it is a known, decided position rather than an oversight; if multi-user access ever lands (Phase 30's owner-token work), revisit. |

**Package changes in this plan:** none.
