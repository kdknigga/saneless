    ## The trap you must not fall into

    `run_pipeline` DOES emit `PipelineEvent.SCANNING` and `PipelineEvent.DONE`. The current
    `if/elif` chain silently ignores both. A naive rewrite that applies `event.job_state`
    whenever it is not `None` would write `JobState.DONE` from INSIDE the pipeline's
    `with tempfile.TemporaryDirectory(...)` block — before cleanup and before `run_pipeline`
    returns. Because the web UI polls once per second, that is user-observable: the "Done"
    panel and the history-refresh `hx-get` would fire early, and any exception during cleanup
    or return would then produce a visible DONE -> ERROR flicker. The existing
    `TestWorkerEnumDispatch` would NOT catch it — it only asserts that `ASSEMBLING` appears
    in `states_seen`.

    ## The fix

    Rewrite `_status_cb` to apply ONLY states that are in `ACTIVE_STATES`. That is derived
    vocabulary, not a new hand-written ignore list, and it naturally excludes `DONE`
    (terminal) while including `SCANNING`. Keep `logger.info("Pipeline event: %s", event.value)`
    as the first statement of the callback.

    Structure: read `state = event.job_state`; if it is `None` or not in `ACTIVE_STATES`,
    set `_transition_event` and return, with a comment explaining that `SCANNING_REVERSE`
    carries no persisted state and that `DONE` is written by the worker AFTER `run_pipeline`
    returns, not from inside it. Otherwise, if the state is in `BUSY_STATES`, call
    `update_state` and THEN `set()`; else (that is `AWAITING_FLIP`) `clear()` FIRST and THEN
    call `update_state`, with a comment noting the UI must not show "busy" while a human is
    being waited on.

    THE ORDERING IS LOAD-BEARING and must be preserved exactly: clear-BEFORE the
    `AWAITING_FLIP` write, set-AFTER the `ASSEMBLING`/`UPLOADING` writes. Note that
    `BUSY_STATES == ACTIVE_STATES - {AWAITING_FLIP}` is precisely the "set after" set — a
    second, independent confirmation that the three-way classification in D-04 is the right
    shape.

    Two benign, deliberate deltas to record in the commit message so they are not mistaken
    for accidents:
    - `PipelineEvent.DONE` now reaches `_transition_event.set()` where it previously matched
      no branch. The event is always already set at that moment (the preceding `UPLOADING`
      set it), and `threading.Event.set()` on an already-set event is a no-op.
    - `PipelineEvent.SCANNING` now produces a second, idempotent `update_state(SCANNING)`.
      The worker already wrote `SCANNING` at line 203 before calling `run_pipeline`, and
      `update_state` is a plain UPDATE, so the only cost is one redundant SQLite write.
      Do NOT special-case `SCANNING` by name to avoid it — that would reintroduce exactly
      the hand-written event list this task deletes.
