<!-- Contracts this plan establishes. Phase 26 (ROBU-05) and Phase 30 (APPL-08) are the consumers. -->

  JobStore.fail_active_jobs(self, reason: str = "Interrupted by restart") -> int
      — @_locked. Sets state to JobState.ERROR and error to `reason` for every row whose
        state is in ACTIVE_STATES. Returns cursor.rowcount.
        Does NOT set error_category — see the action block for why.

  JobStore.list_pending(self) -> list[Job]
      — @_locked. Returns Jobs in JobState.PENDING, ORDER BY created_at ASC.
        Maps rows through the existing private `_row_to_job`.

Module level, built over plan 22-02's name-prefix constants:

  _ACTIVE_STATE_VALUES: tuple[str, ...] — tuple(sorted(s.value for s in ACTIVE_STATES))
  _FAIL_ACTIVE   — over _UPDATE_JOBS, with an IN clause of `?` placeholders sized to _ACTIVE_STATE_VALUES
  _LIST_PENDING  — over _SELECT_ALL, `WHERE state = ? ORDER BY created_at ASC`

"FAILED" in STOR-05, OUTC-01 and the ROADMAP criteria means the EXISTING `JobState.ERROR`.
There is no `JobState.FAILED` and this phase adds none.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `ACTIVE_STATES` frozenset → SQL parameter list | A variable-length `IN` clause whose placeholder count is derived from a set whose iteration order is process-dependent. |
| `fail_active_jobs()` → every non-terminal row | A single unfiltered mass UPDATE across the job table. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-06 | Tampering (SQL injection) | `_FAIL_ACTIVE`, `_LIST_PENDING` in `src/saneless/job.py` | mitigate | Inherits plan 22-02's control and extends it: the only interpolated values are the module-level `_UPDATE_JOBS` / `_SELECT_ALL` literals and a run of `?` characters whose LENGTH comes from the module-level `_ACTIVE_STATE_VALUES` tuple. Every runtime value — the target state, the reason string, each active-state value, the PENDING value — is a bound parameter. `reason` is caller-supplied and is therefore bound, never interpolated. Ruff reports zero `S608` with zero suppressions. |
| T-22-16 | Tampering | `fail_active_jobs()` mass UPDATE | mitigate | The `WHERE state IN (...)` predicate is derived from `ACTIVE_STATES`, and `ACTIVE_STATES` and `TERMINAL_STATES` partition `JobState` (asserted in `vocabulary.py`'s own docstring and tested in Phase 21). A missing or hand-drifted predicate would silently overwrite completed job history. The test asserts terminal rows are unchanged AND that the transitioned set equals `ACTIVE_STATES` computed from the frozenset, so a later phase adding a state cannot leave this method behind. The method ships with no production caller this phase, so the blast radius today is test-only. |
| T-22-17 | Repudiation | the recorded `error` text | accept | `fail_active_jobs()` overwrites any prior `error` on an active row with the restart reason. An active row has not reached an outcome, so there is no completed-job record being destroyed. Phase 23 owns typed outcomes and Phase 26 owns the startup call that will exercise this; no audit requirement exists for a single-operator trusted-LAN appliance. |
| T-22-SC | Tampering | package installs | accept | No packages installed in this phase (RESEARCH § Package Legitimacy Audit). |
</threat_model>
