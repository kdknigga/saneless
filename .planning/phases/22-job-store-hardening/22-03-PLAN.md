<objective>
Serialise every public `JobStore` method on a single `threading.RLock`, move the transaction boundary into method bodies, and make both the lock coverage and the no-public-self-call rule fail the suite the moment someone forgets them.

Purpose: STOR-01. `job.py` today opens one connection with `check_same_thread=False`, exposes seven public methods, and serialises nothing — the review measured 10/10 failures unlocked and 0/10 locked. But a 200-round stress test cannot fail when someone adds an unlocked method next year, and a public method calling another public method silently commits half its work because `sqlite3` connection context managers do not nest. Both need structural tests.

Output: `_LOCKED_MARKER` and the PEP 695 `_locked` decorator in `job.py`, `@_locked` on all public methods with `with self._conn:` moved into the bodies, and three structural tests in `tests/test_job.py`.
</objective>

Module level in `src/saneless/job.py`:

  _LOCKED_MARKER = "__saneless_locked__"
      — the marker attribute name, spelled in exactly one place. The reflective test
        imports this constant rather than repeating the string.

  def _locked[**P, R](
      method: Callable[Concatenate[JobStore, P], R],
  ) -> Callable[Concatenate[JobStore, P], R]

      PEP 695 syntax is REQUIRED, not stylistic: ruff `UP047` rejects the
      `ParamSpec`/`TypeVar`-object spelling outright. `Concatenate[JobStore, P]` is what
      makes `self` typed inside the wrapper so `self._lock` resolves. The marker is set
      with `setattr(wrapper, _LOCKED_MARKER, True)` — a direct attribute assignment makes
      both checkers complain, and `setattr` with a string LITERAL trips ruff `B010`.

      The decorator takes `self._lock` ONLY. It does not open a transaction.

Method contract after this plan — every public method of `JobStore` is
`@_locked`, and every one that executes SQL opens `with self._conn:` in its own body.
`close()` is `@_locked` and has NO `with self._conn:`.

Private helpers (`_row_to_job`, and anything added later) stay UNDECORATED. Shared logic
between public methods goes into a private helper, never into a call to another public method.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker thread ↔ web request threads | Multiple threads share one `sqlite3` connection opened with `check_same_thread=False`. The Python docs state write operations "may need to be serialized by the user to avoid data corruption". |
| public method ↔ public method | With the transaction boundary in method bodies, one public method calling another silently commits the outer transaction's partial work. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-03 | Tampering | every public method of `JobStore` in `src/saneless/job.py` | mitigate | `@_locked` serialises each public method on `self._lock` (a `threading.RLock`), and coverage is proved reflectively over `inspect.getmembers(JobStore, inspect.isfunction)` with NO exemption list, so a future undecorated method fails the suite by itself. The companion `ast` walk asserts no public method calls another, closing the non-nesting-transaction hazard that `RLock` re-entrancy hides (verified: an inner `with conn:` committed the outer transaction and rows survived a rollback that should have discarded them). |
| T-22-04 | Tampering | concurrent mixed reads and writes | mitigate | 2 threads × 200 rounds via `ThreadPoolExecutor` + `Future.result()` — the only mechanism that re-raises a worker's exception in the calling thread; raw `threading.Thread` swallows it and the test would pass green while the store was broken. Zero exceptions is necessary but insufficient (it only re-proves `RLock`'s own contract), so four data invariants are asserted: exact insert count, last-state-set readback, row-count reconciliation, and successful deserialisation of every row. That set is what speaks to ROADMAP criterion 1's "no interleaved-transaction corruption". |
| T-22-13 | Denial of Service | `close()` under `@_locked` | accept | `close()` takes the lock and closes the connection with no transaction context. Use-after-close (`Cannot operate on a closed database`, review finding M-03) is reachable and deliberately NOT fixed here — the `_closed` flag, the saneless-owned use-after-close error, and the shutdown ordering that causes it are all Phase 26's (D-15, user's explicit strict-scope choice against the recommendation). Accepting is a scope decision, not an oversight; do not fold Phase 26's fix back in. |
| T-22-SC | Tampering | package installs | accept | No packages installed in this phase (RESEARCH § Package Legitimacy Audit). |
</threat_model>
