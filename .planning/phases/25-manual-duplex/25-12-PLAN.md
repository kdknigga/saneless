<objective>
Close the three config-load findings: WR-01 (unbounded flip timeout), WR-05 (deprecation warning
emitted before logging exists, so it never reaches `log_file`) and IN-04 (legacy-looking source with
an explicit non-manual `duplex` passes silently).

Purpose: D-18 made the deprecation warning "the only migration instruction an operator will ever
receive". An appliance operator reads the log file; today the warning goes to Python's `lastResort`
handler on stderr only. And D-10's human-facing timeout currently accepts `0` (commonly written to
mean "no timeout"), which throws away every scanned front after pass A.

**Documented choices (planner's call, recorded here, not silent):**
1. WR-01 bounds are `ge=1, le=86_400` (one second to one day). Rationale: 0 and negatives make
   `Event.wait` return immediately and fail every job; anything above `threading.TIMEOUT_MAX`
   (~9.2e9 s) raises `OverflowError` after pass A. A day is far beyond any real flip and far below
   the overflow. D-10 (`int`, default 600, config key in `[output]`) is unchanged. "0 means no
   timeout" is deliberately NOT adopted: an unbounded human wait is exactly M-07's complaint.
2. WR-05 moves the *emission* of the named warning out of the `Settings` field validator into a
   module-level function `warn_on_legacy_duplex_sources(settings)` that `cli()` calls right after
   `configure_logging`. D-03's substance is preserved: translation stays in the `ProfileConfig`
   before-validator (every construction path), naming stays at the settings level (a profile still
   cannot name itself), once per load, `logger.warning` on `saneless.config` (D-04), replacement stated
   inline (D-18). Consequence, accepted: constructing `Settings(...)` programmatically no longer logs;
   every operator entry point (`scan`, `serve`, `devices`, `jobs`, `auto-profiles`) runs through the
   `cli()` group callback, and `load_settings` is called only from `cli.py`.
</objective>
