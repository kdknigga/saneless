<objective>
Remove the duplicated claim-once concurrency code (IN-02), fix the CLI prompt thread hanging on an
unexpected exception (WR-08), and correct a stale docstring (IN-01).

Purpose: `WorkerFlipCoordinator` (worker.py) and `ClickFlipCoordinator` (cli.py) each carry the same
lock + event + outcome + `_resolve` code with the same comments. The review predicted exactly what
happened in 25-10: CR-01's fix touched one of them. One implementation means the next fix lands in
both. WR-08: `_prompt` handles only `click.Abort`; any other exception kills the thread silently, the
main thread waits the full 10 minutes, and the job fails with "nobody confirmed", which is false.

Ordering: this runs after 25-10 (which added arming and bool-returning signals to the web
coordinator) and 25-12 (which edited cli.py and the CLI timeout test), so it refactors the final
shapes. D-09's `FlipCoordinator` ABC is unchanged: `FlipAnswerSlot` is a concrete helper both
implementations compose, not a new abstract seam. Arming stays in `WorkerFlipCoordinator` only -- the
CLI prompt starts inside `wait_for_flip`, so it has no early window to guard.

**Documented choice (WR-08):** an unexpected prompt failure resolves `FlipOutcome.ABORTED`, not
`TIMED_OUT` and not a new fourth outcome. `TIMED_OUT`'s message ("nobody confirmed the stack was
flipped") would be false; a fourth outcome would reopen D-09's total three-member enum for a failure
the operator experiences as "the prompt broke, so the scan stopped". The logged traceback carries the
real cause, and D-15 already makes an abort a plain `ScanError`.
</objective>
