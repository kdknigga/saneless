<objective>
Finish CR-01's route half: the flip routes must stop re-rendering a stale `AWAITING_FLIP` prompt,
buttons included, as though the click did nothing. That re-render is what invited the verifier's
double-click in the first place.

Purpose: after 25-10 a repeated click is harmless (it is dropped), but the UI still lies by omission:
the response to a claimed Abort is the same flip prompt the operator just clicked, because the worker
thread has not yet persisted `ERROR`. The user decision for this gap pass is that routes "must not
blindly re-render a stale AWAITING_FLIP partial as if the signal was claimed".

**Documented design choice (planner's call, within D-16):** D-16 rejected "having `continue_flip`
render a busy partial without re-reading the job", because "the route would assert a state the store
has not recorded". This plan does NOT do that. The route still re-reads the job through D-17's shared
`_current_or_recent_job`, and the store's state is still what selects the branch. What changes is
that the `AWAITING_FLIP` branch now also consults a fact the worker genuinely holds -- whether that
job's flip wait has already been answered, and with what (`ScanWorker.flip_answer(job_id)`, added in
25-10) -- and renders "answer received" copy instead of the buttons when it has. No state the store
has not recorded is claimed; D-16's "the control disappears on its own" is extended to the gap
between the answer being claimed and the worker persisting the next state. The acknowledgment copy
below is new UI copy; 25-15 records it in `.planning/UI-SPEC.md`.

Output: `flip_answer_label` in the vocabulary, a registered filter, a shared status-context builder in
routes, the acknowledgment branch in `status.html`, route tests, and a Playwright test that clicks
the real button.
</objective>
