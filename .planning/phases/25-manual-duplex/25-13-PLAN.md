<objective>
Close the three scanner/auto-profiles warnings: WR-02 (a both-sides feeder accepted as if
single-sided), WR-03 (manual duplex regressed on devices with no `source` option) and WR-04
(`is_bare_default` ignores `duplex`, so a manual-duplex default is silently overwritten in memory).

Purpose: each ends in the failure mode this phase exists to remove -- a job that reports success for
the wrong document (WR-02, WR-04) -- or in a regression against success criterion 1's "still loads
and scans" (WR-03).

**PRODUCT DECISION -- flagged, not silent (WR-02).** D-02 (locked) says the backend "picks the first
source classifying `FEEDER` or `FEEDER_DUPLEX`". Read literally that allows today's behaviour. The
review shows what that produces: on a duplex source each pass returns 2N pages, the counts agree,
`_interleave_duplex` pairs front+back with reversed back+front, and the job ends `DONE` with 4N pages
in scrambled order and no warning. D-02's own rationale (and C-01) is to never return a green result
for the wrong document. This plan therefore narrows D-02 as follows, and records it as a deliberate
choice for the user to overrule before execution if they disagree:
1. A reported `SourceKind.FEEDER` always wins over a `FEEDER_DUPLEX` one. If the profile named a
   reported `FEEDER`, that one; else the first reported `FEEDER` in device order.
2. If the profile named a reported `FEEDER_DUPLEX` source and a `FEEDER` exists, the `FEEDER` is used
   and a WARNING names both (the operator's choice is overridden, loudly, because honouring it
   scrambles the document).
3. If the device's only feeders are `FEEDER_DUPLEX`, manual duplex is **refused** with `ScanError`
   before any page (the review's "or refuse it" branch), not used with a WARNING: in an unattended
   appliance a WARNING beside a green `DONE` is the silent corruption D-02 exists to prevent. The
   message tells the operator to use `duplex = "hardware"`.
Alternative rejected: "use FEEDER_DUPLEX as last resort with a WARNING".

**WR-03 scope choice.** When the device exposes no `source` option, nothing is assigned to the
device, so the both-sides concern in WR-02 does not arise; the configured name is only evidence of
whether the device feeds. The branch therefore trusts `classify_source(requested).uses_feeder`
(FEEDER or FEEDER_DUPLEX), exactly as the simplex path does on the same device. This is what restores
the legacy `source = "Manual Duplex"` profile (classifies FEEDER_DUPLEX) on such hardware.

**WR-04 consequence, accepted.** Whole-profile equality also stops auto-generation for a single
`default` profile customised in any other field (e.g. `paper_size`, `default_tags`). That is the
review's intent ("so that no field added later can repeat this") and is strictly more conservative:
auto-profiles only ever fills in a config the operator has not touched.
</objective>
