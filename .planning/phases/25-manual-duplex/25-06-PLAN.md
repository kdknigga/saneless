<objective>
Make manual duplex actually reach a feeder. Resolve the device source from the device's own reported
list using Phase 24's classifier, and refuse rather than silently substituting `Auto`.

Purpose: this is the wave that closes C-01. Today `"Manual Duplex"` is handed to SANE verbatim, so
`_resolve_source` either raises or — on a device exposing `Auto` — silently substitutes it and, with
`auto_source_mode` defaulting to `flatbed`, takes **one platen snapshot per pass** and reports a green
Complete. Either way the documented feature does not work.

Output: a narrow signal on `ScanSettings`, a disjoint selection branch in `_resolve_source`, and an
integration test driving the real backend against a realistically named feeder.
</objective>

**Wave 0 enabler carried by this plan:** `tests/test_pipeline.py:815` currently calls
`dev.report_sources(["Flatbed", "ADF Manual Duplex"])` — it makes the pseudo-source *real* so the
test can pass. Until that line carries a realistic list, the integration test still asserts the
fiction C-01 exists to remove.

**Do not hardcode `"ADF"`.** The code review suggests it and D-02 **declines it outright**. Phase 24
established that real feeders are named `"Automatic Document Feeder"` (Epson, Canon, Brother) and
`_resolve_source` validates against the device's actual list, so a hardcoded `"ADF"` would fail on
precisely the consumer hardware manual duplex exists for. `tests/fake_sane.py:109`'s
`_DEFAULT_SOURCES` is `["Flatbed", "Automatic Document Feeder", "ADF Duplex"]` with **no plain
"ADF"**, which makes any test against the default fake an automatic regression guard for this.

**Three planner discretion calls recorded:**

1. **What `ScanSettings` carries: `resolve_feeder_source: bool`.** Options weighed were a
   scanner-side `DuplexMode` enum beside `SourceKind`, an empty-string sentinel, and this boolean.
   The enum loses on this codebase's own rule: its `NONE` and `HARDWARE` members would behave
   **identically** inside the scanner — two members, one behaviour — which is precisely the
   "member with no reader" D-05 argues against at the config layer. A boolean named for what the
   backend actually does creates no second spelling of "duplex", keeps D-01's `Literal` as the single
   spelling in the codebase, and gives exactly one conversion point (in `run_pipeline`). It also
   keeps Phase 21 D-03 intact: `grep -rn "vocabulary|JobState|ScanOutcome" src/saneless/scanner/` is
   empty today and must stay empty. `auto_source_mode` is the exact in-tree precedent for a
   scan-strategy flag carried in settings and read by the backend.
2. **A device with no feeder source refuses.** CONTEXT leaves this open with one hard constraint: the
   `Auto` substitution must not be reachable for manual duplex. Refusing (rather than proceeding) is
   the conservative branch — proceeding would take two platen snapshots on a fixed-flatbed device,
   C-01's exact failure. A device exposing **no** `source` option at all is treated the same way
   (assumption A2).
3. **The operator's `source` is still preferred when the device reports it and it feeds.** This
   reconciles D-01 ("`source` is passed to the device verbatim"), D-02 ("resolved at scan time from
   the device's own source list") and D-18 (the how-to teaches `source = "ADF"` + `duplex =
   "manual"`). Under the alternative — ignore `source` entirely whenever `duplex == "manual"` — the
   `source` value D-18 tells operators to write becomes decorative, and an operator who deliberately
   selects one of two feeders silently gets the other. Device resolution is the **fallback**, not the
   override. This is a judgement call at the seam between two locked decisions and is recorded rather
   than assumed.
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SANE device → saneless | The device supplies its own source-name strings, which reach classification, selection and error messages |
| operator profile `source` → device option assignment | An operator-written string is matched against the device's reported list |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-25 | Tampering (silent wrong-source scan) | the `Auto` substitution reachable for manual duplex | mitigate | The feeder path is a **disjoint branch**, so the substitution is structurally unreachable rather than guarded. This is C-01's mechanism: with `auto_source_mode` defaulting to `flatbed`, substitution produces two platen snapshots and a green Complete — a silent wrong result, which is worse than a loud failure |
| T-25-26 | Spoofing (device-supplied name) | a device source name reaching selection and error text | mitigate | Names are never executed, never used to build a path, and never interpolated into a shell. They are matched against the device's own reported list and classified by the single `classify_source` rule; the refusal message renders the list through `%`-style logging/formatting |
| T-25-27 | Denial of Service | an unbounded feeder loop re-scanning a platen | accept (already mitigated) | `_MAX_ADF_PAGES = 500` bounds each `scan_pages` call and is therefore **per pass** (Phase 24 D-04). No change needed; recorded so the duplex path's bound is explicit |
| T-25-28 | Tampering (operator intent overridden) | device resolution silently replacing a deliberately chosen feeder | mitigate | The requested source wins when the device reports it and it feeds; resolution is the fallback. An operator who picks one of two feeders gets that one |
| T-25-SC | Tampering | package installs | N/A | This phase installs nothing |
</threat_model>
