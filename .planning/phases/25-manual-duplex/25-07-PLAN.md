**Wave 0 enabler carried by this plan, and the single highest-risk omission in the phase.**
`CliRunner` reports `sys.stdin.isatty() is False` (measured). A refusal written directly as
`if not sys.stdin.isatty(): sys.exit(2)` therefore fires inside **every** `CliRunner` test —
including the one meant to reach `click.confirm`. Written naively, D-11's two halves are **mutually
untestable**. The one-line `_stdin_is_interactive()` indirection is what resolves it: the refusal test
runs unpatched (honest — `CliRunner` genuinely is not a terminal), and the prompt test patches the
seam. Neither test lies. **Write the seam first.**

**`click.pause` is disqualified, not merely dispreferred.** It is the only API matching the roadmap
criterion's "press Enter" wording literally, and the click documentation states twice that it is a
**no-op when not run through a terminal** (re-confirmed by execution this phase: off a terminal it
printed nothing and returned immediately). Using it would silently resume and re-scan the fronts as
backs — C-02 verbatim — and the suite would not catch it, because `CliRunner` is not a TTY either.

**This is the CLI's first interactive read.** Verified by reading all 386 lines of `cli.py`: there is
no `isatty`, no `click.confirm`, no `click.prompt` and no `input()`. Every interaction today is
one-way `click.echo`. Use RESEARCH.md Code Examples 4 and 5 (both executed against click 8.3.1)
rather than hunting for an in-tree pattern.

**Measured `CliRunner` + `click.confirm` behaviour, which the tests depend on:** the prompt text **is
echoed into `result.output`** between surrounding echoes (so the ordering assertion works verbatim);
answering `n` returns `False` cleanly at exit 0; EOF raises `click.Abort` → exit 1.

**Two planner discretion calls recorded:**

1. **`ClickFlipCoordinator` catches `click.Abort` and returns `FlipOutcome.ABORTED`** rather than
   letting it propagate as exit 1. Otherwise Ctrl-C at the prompt and clicking Abort in the web UI
   produce *different* job outcomes for the same operator intent, fragmenting what Phase 28's EXC-04
   will later have to classify.
2. **The CLI coordinator accepts and documents away the timeout — see the flagged conflict below.**

**⚠ FLAGGED CONFLICT — the CLI cannot honour `wait_for_flip`'s timeout.** D-09 locks the signature
`wait_for_flip(timeout: float) -> FlipOutcome`, and DPLX-05 requires a timeout that fails the job.
But `click.confirm` blocks on stdin and has **no timeout facility**; implementing one needs `select`
on stdin or a second thread. M-07's actual complaint was the *web* worker thread parking behind a
queue, which `WorkerFlipCoordinator` does cover — the CLI has no queue behind it and the operator can
press Ctrl-C. **Resolution for this plan:** `ClickFlipCoordinator.wait_for_flip` accepts the parameter
and ignores it, naming it `_timeout` (ruff `ARG002` honours the configured `dummy-variable-rgx`;
in-tree precedent is `pipeline._noop_callback(_event)` at `:148-149` and `cli.devices(_settings)` at
`:211`), and its docstring states plainly that this implementation blocks on stdin and returns only
`CONTINUED` or `ABORTED`, never `TIMED_OUT`, with the reason. DPLX-05 and roadmap criterion 3 are
satisfied through the **worker** coordinator, proven by plan 25-05's e2e case. **This narrows
DPLX-05's plain reading and may warrant a roadmap criterion amendment — raised to the developer
rather than decided silently.**
