**Wave 0 enabler carried by this plan, and the single highest-risk omission in the phase.**
`CliRunner` reports `sys.stdin.isatty() is False` (measured). A refusal written directly as
`if not sys.stdin.isatty(): sys.exit(2)` therefore fires inside **every** `CliRunner` test —
including the one meant to reach `click.confirm`. Written naively, D-11's two halves are **mutually
untestable**. The one-line `_stdin_is_interactive()` indirection is what resolves it: the refusal test
runs unpatched (honest — `CliRunner` genuinely is not a terminal), and the prompt test patches the
seam. Neither test lies. **Write the seam first.**

**`click.pause` is disqualified, not merely dispreferred.** It is the only API matching the roadmap
criterion's original "press Enter" wording literally, and the click documentation states twice that
it is a **no-op when not run through a terminal** (re-confirmed by execution this phase: off a
terminal it printed nothing and returned immediately). Using it would silently resume and re-scan the
fronts as backs — C-02 verbatim — and the suite would not catch it, because `CliRunner` is not a TTY
either. Roadmap criterion 2 has already been reworded for this reason; **no task here edits
ROADMAP.md.**

**This is the CLI's first interactive read.** Verified by reading all 386 lines of `cli.py`: there is
no `isatty`, no `click.confirm`, no `click.prompt` and no `input()`. Every interaction today is
one-way `click.echo`. Use RESEARCH.md Code Examples 4 and 5 (both executed against click 8.3.1)
rather than hunting for an in-tree pattern.

**Measured `CliRunner` + `click.confirm` behaviour, which the tests depend on:** the prompt text **is
echoed into `result.output`** between surrounding echoes (so the ordering assertion works verbatim);
answering `n` returns `False` cleanly at exit 0; EOF raises `click.Abort` → exit 1.

**One planner discretion call, and one developer decision taken after planning:**

1. **Discretion — `ClickFlipCoordinator` catches `click.Abort` and returns `FlipOutcome.ABORTED`**
   rather than letting it propagate as exit 1. Otherwise Ctrl-C at the prompt and clicking Abort in
   the web UI produce *different* job outcomes for the same operator intent, fragmenting what Phase
   28's EXC-04 will later have to classify.
2. **D-19 — the CLI honours `wait_for_flip`'s timeout by prompting on a daemon thread.** Not planner
   discretion; see immediately below.

**RESOLVED — the CLI honours the timeout (D-19; RESEARCH.md § "Open Questions (RESOLVED)" Q1).**
Planning first proposed that `ClickFlipCoordinator` accept its timeout and ignore it, on the grounds
that `click.confirm` blocks on stdin with no timeout facility and that M-07's actual complaint was
the *web* worker thread parking behind a queue. The plan-checker escalated that as a **BLOCKER**:
DPLX-05 carries no CLI/web carve-out, and the phase goal itself says the coordinator "serves both CLI
**and web**". **The developer decided the CLI honours the timeout.** DPLX-05 is therefore **not**
narrowed, and neither it nor roadmap criterion 3 needs amending — both are literally true on both
paths.

- **Mechanism:** run `click.confirm` on a **daemon** thread which records its answer through the
  coordinator's single-answer claim and sets a `threading.Event`; the calling thread waits on that
  event for `timeout` seconds and claims `FlipOutcome.TIMED_OUT` when it expires. D-11's locked
  `click.confirm` is preserved untouched, so C-02's prescribed `CliRunner` prompt-echo ordering
  assertion still works verbatim — which is precisely why `select.select` on stdin was rejected (it
  reopens D-11, loses `click.confirm`'s y/n parsing and its `Abort`-on-interrupt behaviour, and
  forces C-02's assertion to be rewritten).
- **Measured before the decision was taken — do not re-derive:** a daemon thread blocked on a stdin
  read does **not** delay interpreter shutdown. `elapsed_in_python=0.200s`, `real 0m0.223s`, reader
  thread still alive at exit, timed against a never-EOF FIFO so the interpreter alone was measured.
- **Accepted cost, which must be written into the docstring:** after a timeout the orphaned thread
  still holds stdin until the process exits, and a stray prompt may be left on the terminal. Bounded,
  because the job has already failed and the CLI is on its way out.

    `wait_for_flip` starts a `threading.Thread(target=..., daemon=True)` whose body calls
    `click.confirm` with a message telling the operator to flip the stack and reload it, and resolves
    `FlipOutcome.CONTINUED` on a yes and `FlipOutcome.ABORTED` on a no — catching `click.Abort`
    (raised on Ctrl-C or EOF) and resolving `ABORTED` there too, so an interrupted prompt and a web
    Abort produce the same job outcome. `daemon=True` is load-bearing: a non-daemon thread still
    parked on stdin would hold the interpreter open at exit, which is the whole reason the daemon
    form was measured before D-19 was taken. Do **not** catch a bare `Exception` in the thread body
    (ruff `BLE001`); an unexpected escape simply leaves the event unset and the bounded wait covers
    it, which is the correct fallback.

    claimed outcome; if the wait expires, claim `FlipOutcome.TIMED_OUT` through `_resolve` and return
