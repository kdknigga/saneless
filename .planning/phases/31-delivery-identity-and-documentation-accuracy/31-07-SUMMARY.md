## Accomplishments

### Row 30 — the job id came off the source, not off the page

The example showed `"id": "a1b2c3d4"`. The id is read straight out of the row by the CLI's JSON branch (`cli.py:831`, `"id": j.id`), and a job id is `str(uuid.uuid4())` (`job.py:704` and `:793`). The example now carries `8eae6099-6b24-4b69-a339-8daa8e6c9a5c` -- a value generated by `uuid.uuid4()` rather than typed to look like one, so its version and variant nibbles are what they have to be.

While the serialiser was open, the other six fields were checked against it rather than assumed correct:

| Field in the example | What `cli.py` emits | Verdict |
|---|---|---|
| `id` | `j.id` -- a UUID4 string | **was wrong**, corrected |
| `profile` | `j.profile` | matches |
| `title` | `j.title` | matches |
| `state` | `j.state.value`, raw uppercase enum | matches |
| `created_at` | `j.created_at.isoformat()`, UTC | matches, offset already present |
| `outcome` | `j.outcome.value` or `null` | matches |
| `warning` | `j.warning` | matches |

Field order in the example is the serialiser's order too. One `"id"` exists on the page; the contract scans every one of them, so a second example cannot be added in the old shape.

### Row 31 — the flag form, and only the flag form

`quick-start.md:23` was the single live offender, which is what the red contract named. `which-setup.md`'s two `docker run` blocks, added by plan 06 the same day, were already written in the absolute form and are now held there by the same contract.

The distinction the contract draws is the point of it:

| Syntax | Correct host side | Why |
|--------|-------------------|-----|
| `docker run -v` / `--volume` | `"$(pwd)/config:/etc/saneless"` | Docker Engine has historically rejected a relative host path outright; the quoting keeps a directory whose name contains a space as one argument |
| compose `volumes:` entry | `./config:/etc/saneless` | resolved against the compose file, correct, and the mount Phase 27 D-09 requires |

`grep -rn '\-v \./' docs/` returns nothing. `docker-compose.yml` is untouched -- its directory-mount count is still 1.

### Row 32 — a pointer instead of half a stack (DOCS-06, D-49)

The compose example declared a service for the other project with one setting, `PAPERLESS_SECRET_KEY`, and neither a database nor a message broker. The stack it described cannot come up, so a reader who followed the guide got a container restarting forever with nothing saying why.

The example is now saneless alone, preceded by a note that sends the reader to [the paperless-ngx setup guide](https://docs.paperless-ngx.com/setup/) and [their compose directory](https://github.com/paperless-ngx/paperless-ngx/tree/main/docker/compose) -- both URLs taken from paperless-ngx's own `docs/setup.md` via Context7 rather than from memory.

Removing the service made two facts load-bearing that the old example had quietly assumed away, and both are now stated rather than implied:

- **Name resolution.** Two compose projects get two networks, so `paperless` does not resolve from the saneless container on its own. The page gives both routes -- join their network (commented `networks:` blocks on the service and at the top level, with `docker network ls` named as the way to find the real name rather than a project name hard-coded here) or point `url` at the host and published port -- and says why `localhost` is not one of them.
- **The consume directory.** It is now described as a volume created once outside both projects and declared external on each side, which is what sharing across compose projects actually requires. The old text said "uncomment the volume on both services", which stopped being possible the moment the other service left the file.

The live YAML was parsed to confirm the example still loads and still declares exactly the saneless service with its two required mounts. `## Running behind a reverse proxy` is intact -- plan 06's DOCS-05 sentence links to it.

## Decisions Made

**The job id was derived twice over.** Reading `job.py` gives the generator; reading `cli.py`'s `--json` branch confirms the CLI does not reshape it on the way out. Plan 31-05's finding -- that docs and their own doc-truth tests can agree with each other while both have stopped agreeing with the code -- is why the second read happened, and it is also why the remaining six fields were checked rather than trusted.

**`Redis-compatible message broker`, not `Redis`.** Their FAQ says the bundled compose files default to Valkey and that any wire-compatible broker works. Writing "Redis" would have been a smaller version of exactly the mistake D-49 rejects: a claim about someone else's stack that was already drifting.

**The network name is a lookup, not a literal.** The commented `networks:` block gives `paperless-ngx_default` as an example and tells the reader to confirm it with `docker network ls`, because compose derives that name from whatever directory their file happens to run in. Hard-coding it would have re-introduced the dependency on their conventions that this task existed to remove.

## Issues Encountered

**The self-inflating grep trap was live again and was avoided deliberately.** Two acceptance criteria are `grep -c` counts over single documentation files (`a1b2c3d4` in the scripting guide, `PAPERLESS_SECRET_KEY` in the deploy guide) while the strings themselves have to appear in the test file. The contracts live in `tests/`, which neither grep scans, so no rewording was needed -- but the marker constant is still written as a concatenation rather than a literal, so a future criterion that widens its scope to the tree does not get a false count from the file whose job is to ban the thing.

**`mkdocs build --strict` exits 0 on an INFO it also wants you to fix.** The not-in-nav line was an INFO, not a warning, so `--strict` never failed on it and the page stayed published for however many releases. The contract added here is what actually stops it recurring; the clean build is a consequence, not the guard.
