Verification-host caveat: `docker` on this machine is podman/buildah 1.39.4, rootless, with SELinux
Enforcing. Rootless podman maps host UID 1000 to container UID 0, so a bind-mounted host directory
owned by 1000:1000 appears as 0:0 inside and container UID 1000 cannot write it. If a bind-mount
check is run at all, it needs `--userns=keep-id:uid=1000,gid=1000` AND a `:Z` mount suffix. Neither
the `pip install` half nor the `--version` / `id` checks are affected. A failure caused by these two
flags is a property of the verification host, not of the image — do not "fix" the image for it.

Docs-site verification (criterion 5, blocker 5): after `docs.yml` has run green with Pages source
set to GitHub Actions, fetch each `kdknigga.github.io/saneless/<path>/` link from `README.md` and
assert HTTP 200. Plan 02's `test_every_readme_docs_link_resolves_to_a_page` already proves the link
targets exist as FILES; this proves they resolve as PUBLISHED pages, which is the half that needs
the site to have deployed at least once.

`31-AUDIT.md` (Plan 08) has a clearly-marked placeholder section for this evidence. Fill it; do not

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public registries (TestPyPI, GHCR) -> a clean verification machine | The artefacts are fetched and executed as an anonymous consumer would fetch and execute them |
| GHCR package visibility -> the world | Making a package public is one-way |
| the final `v0.2.0` tag -> real PyPI | The first successful publish claims the project name permanently and the version number can never be reused |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-36 | Spoofing | the published artefacts | mitigate | Verification pulls from the real registries into throwaway containers and RUNS the result — `saneless --version` from the installed wheel, `--version` and `id` from the pulled image. Reading the workflow file is explicitly not evidence (the user's own standard for criterion 2). Attestations and provenance were attached at publish time by Plan 04 |
| T-31-08 | Elevation of privilege | the published image's runtime user | mitigate | `docker run --rm --entrypoint id <published image>` must print `uid=1000` — proving the non-root work survived the build-and-publish path, not just the local build |
| T-31-21 | Tampering | `latest` or a plain `pip install saneless` resolving to a pre-release | mitigate | Both halves are asserted against the live registries after the rehearsal: `docker manifest inspect ...:latest` must fail or resolve elsewhere, and `https://pypi.org/pypi/saneless/json` must still return 404. This is the first moment D-23's constraint is observable rather than argued |
| T-31-37 | Information disclosure | GHCR package visibility | accept (user decision) | Making the package public is required for an anonymous pull and is one-way. The image contains only the built wheel and OS packages — the `.dockerignore` allow-list and the explicit `COPY` lines keep any real config out — so the disclosure is the software itself. The user is told it is one-way before deciding, and declining is a recorded outcome, not a silent skip |
| T-31-06 | Tampering | the final release tag | mitigate | Not a task. The commands are written down for the user; the `pypi` environment's Required-reviewers rule means even an accidental push waits for a human click. Claude creates no tag at any point in this phase |
| T-31-31 | Repudiation | the audit artifact's rehearsal section | mitigate | Verbatim command output, the tag name, the commit SHA and the run URL are recorded; anything not actually observed is recorded as blocked with a reason rather than as passed |
</threat_model>
