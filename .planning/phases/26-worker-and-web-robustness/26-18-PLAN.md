<objective>
Close WR-10, the one open verification gap on success criterion 1. Close WR-11 in the same pass,
because it lives in a test this plan has to change anyway.

Purpose: 26-15 made `_idle_housekeeping` (src/saneless/worker.py lines 788-821) retry owed job-row
writes on every non-degraded idle tick. A failed retry is only logged at DEBUG and never counted. The
guard's own failure counted 1 of `_DEGRADED_AFTER = 3`. Nothing else can add to that count: the stuck
active row disables `#scan-btn`, so no new job runs, and the retries are excluded by design. A request-side
debt from `owe_rejection` (26-17) was never counted at all. So when the store keeps refusing writes
(full disk, read-only remount, a lock held by another process), `/health` stays 200 and the status area
shows the stuck row as live. Only a later hourly `prune` failure reaches degraded, about 2 hours in.
The verifier reproduced this: `finish_calls=100 health=HEALTHY row_state=PENDING consecutive_loop_failures=1`.

Fix (per 26-VERIFICATION.md gaps[0].missing and 26-REVIEW.md WR-10's suggested fix, adapted): count
failed flush ticks in their own streak counter. Degrade once the streak reaches a threshold. Do not
fold the streak into `_consecutive_loop_failures`. Why a separate streak:
- A guard debt starts at 1 and a rejection debt at 0, so folding would give two different bounds.
- 26-15's reason for not double-counting the guard's failure still holds.

The threshold is its own module constant `_OWED_RETRY_DEGRADED_AFTER` (3, the same "ride out one or two
transient errors" reasoning as D-10). It is read at call time, so the heal-path tests that deliberately
observe a failing window can raise it. The new streak tests use the production value.

Recovery (the "what recovers from degraded" question): unchanged in shape. A streak-degraded worker goes
through `_try_recover` on each tick. Degraded clears only when the probe succeeds AND
`_flush_unrecorded_failures()` returns, which proves the owed rows landed. That success also resets
`_failed_flush_ticks`, so a fault that comes back needs a fresh streak.

This explicitly SUPERSEDES 26-15's must-have "A failed retry of an owed write is logged at DEBUG and does
not count towards degraded". It also supersedes the "never counting a failed retry" wording in 26-17's
`TestOwedRejections`. A failed retry is still never a *loop-level* failure, but a streak of them now
degrades.

Output: RED tests for the persistent-fault degrade, the recovery, the sub-threshold heal and the web
`/health` 503. GREEN worker change plus adjusted superseded tests. The WR-11 race fix. The architecture
and web-api docs updated.

Out of scope:
- WR-10's "related gap" (the flush aborts at the first raising entry). SQLite write faults are
  database-wide, and changing it would multiply failing calls per tick and the call-count assumptions
  of existing tests.
- IN-08 (plan 26-19).
- WR-02..WR-09, IN-01..IN-07.
- Resetting `_consecutive_loop_failures` on a non-degraded flush success.
