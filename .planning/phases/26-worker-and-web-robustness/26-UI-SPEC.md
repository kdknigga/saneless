# Phase 26 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This is a hardening phase on an existing, styled UI. It adds no screen, no palette, no type tier, and does not restyle anything. Five UI surfaces change, and this contract pins each one:

| # | Surface | Requirement / decision | Files |
|---|---------|------------------------|-------|
| S1 | Vendored asset tags + `htmx-config` meta | ROBU-09, D-01, 23.1 coupling contract | `base.html`, `static/vendor/` |
| S2 | Request error message slot `#status-message` | D-01..D-04, D-22, ROBU-02, ROBU-08 | `index.html`, `partials/error.html` (new), `app.css` (one rule) |
| S3 | Error copy: slot messages, rejected-row texts, restart reason | D-05, D-13, D-22, research § Security | `vocabulary.py` (copy owner), renderer |
| S4 | Server-owned Scan button | ROBU-04, ROBU-11, carried-forward button rule | `partials/scan_button.html` (new), `partials/status_response.html` (new), `index.html`; `static/app.js` deleted |
| S5 | Title input length cap | ROBU-08 | `index.html` (one attribute) |

**Everything not named here is inherited unchanged** from `.planning/UI-SPEC.md` (master) and `.planning/phases/23.1-dark-mode-and-the-commit-gate/23.1-UI-SPEC.md`: layout, cards, status-area presentations, flip prompt, history table, spacing, typography, colours, dark-scheme convention.

## S1 — Vendored Asset Contract (ROBU-09)

### Coupling contract from 23.1 (LOCKED, restated verbatim as obligations)

1. Vendor **`pico.min.css` v2.1.1** only.
2. Do **not** vendor or link `pico.colors.css`.
3. Reintroduce **no** `data-theme` attribute on `<html>`. Line 2 of `base.html` stays exactly `<html lang="en">`.
4. Keep the `--saneless-status-fallback` block in `app.css` intact (the `:root` light value, the `@media only screen and (prefers-color-scheme: dark) { :root:not([data-theme]) }` block, the `[data-theme="dark"]` block, and `.status-fallback { color: var(--saneless-status-fallback); }`).
5. Move the DARK-01 / DARK-02 browser tests into CI now that assets are local (they run under the new `browser` CI job, behind the no-egress gate in the Verification Contract).

### `base.html` `<head>`: exact order and markup

```html
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<meta name="color-scheme" content="light dark">
<meta name="htmx-config"
      content='{"responseHandling":[{"code":"204","swap":false},{"code":"[23]..","swap":true},{"code":"[45]..","swap":true,"error":true}]}'>
<title>saneless</title>
<link rel="stylesheet" href="/static/vendor/pico-2.1.1.min.css"
      integrity="sha384-L1dWfspMTHU/ApYnFiMz2QID/PlP1xCW9visvBdbEkOLkSSWsP6ZJWhPw6apiXxU">
<link rel="stylesheet" href="/static/app.css">
<script src="/static/vendor/htmx-2.0.8.min.js"
        integrity="sha384-/TgkGk7p307TH7EXJDuUlgG3Ce1UVolAOFopFekQkkXihi5u/6OCvVKyz1W+idaz"></script>
```

Rules:
- **Cascade order is unchanged:** Pico, then `app.css`, then htmx, all in `<head>`, htmx loaded synchronously (no `defer`/`async`, as today). Changing the order would change which rule wins and is forbidden.
- **`htmx-config` restates all three `responseHandling` entries.** htmx 2.0.8 merges meta config shallowly; a meta holding only the `[45]..` entry replaces the array and stops every 2xx swap.
- **No `crossorigin` attribute** (same-origin SRI). **No `http://` or `https://` URL in any template.**
- `<body>` ends with `</main>` then `</body>`: the `<script src="/static/app.js">` line is removed, not commented out.

## S2 — Request Error Message Slot (D-03)

### Placement and markup

`index.html`, between the Scan `</article>` and the status include:

```html
</article>

{# --- Section 2: Request errors, then status --- #}
<div id="status-message" role="alert"></div>
{% include "partials/status.html" %}
```

- **Sibling of `#status-area`, placed directly above it** **[default]**. Reason: the slot sits immediately under the Scan button the user just pressed, and it is never pushed below the fold by the flip prompt's two SVGs or the 300 px thumbnail, which render inside `#status-area`. D-03 requires only "a sibling next to the polled `#status-area`".
- It is **outside** `#status-area`, so the 1 s `outerHTML` poll never replaces it.
- It is **outside** the `<form>`, so it is not affected by `hx-disabled-elt` / `hx-disinherit`.
- Exactly **one** `id="status-message"` on the full page. It appears in no partial except as the OOB clear element (below).
- The template writes the element with **no whitespace between the tags** (`<div …></div>`).

### Empty state

- Empty means **no child nodes**. With no children, no padding, no border and no margin of its own, the div has a **computed height of 0 px** and adds no gap. `#status-area`'s top edge is at the same y as it was before this phase.
- An empty `role="alert"` region announces nothing.
- No CSS rule targets `#status-message` itself. There is no `:empty` rule, no placeholder text, and no reserved height.

### Error partial `partials/error.html` (new; the only markup the renderer emits for htmx requests)

```html
<p class="status-error">&#10007; {{ message }}</p>
{% if refresh_history %}<div hx-get="/api/jobs/history" hx-target="#history-body" hx-swap="outerHTML" hx-trigger="load" class="htmx-hidden"></div>{% endif %}
```

- `message` is always a developer-authored constant from the copy table in S3. It is autoescaped, and it **never** contains request input (profile name, title, query value, header value) or exception text.
- **No `role="alert"` on the `<p>`.** The container already is the alert region; a nested alert makes some screen readers announce the message twice.
- **No `id="scan-btn"`, no `hx-swap-oob`, no `id="status-area"`** in an error response. An error changes neither the button nor the status area.
- **Glyph prefix without "Error:" [default].** `✗` (U+2717) marks it as the same family as the status area's error line. The word "Error:" is dropped because every slot message is a complete sentence that names its own problem, and several (403, 422) are not failures of the scan.
- `refresh_history` is **true only** for the D-05 rejection responses (429 queue full, 503 unavailable or degraded from `POST /api/scan`), and only when the rejected row was actually written. It reuses the terminal-status history loader verbatim, so the rejected attempt shows up in Job History at once (D-05: "the user wants the attempt visible") without a reload. The loader is `display: none` and has no text, so it adds nothing to the announcement.

### Response headers (htmx branch)

| Header | Value | When |
|---|---|---|
| `HX-Retarget` | `#status-message` | every 4xx/5xx with `HX-Request: true` (D-02) |
| `HX-Reswap` | `innerHTML` | same. This replaces the slot's **children**, so the container and its `role="alert"` survive |
| `Retry-After` | the fixed integer chosen by the planner (research discretion) | every 429, on **both** branches (D-04) |

Non-htmx requests (no `HX-Request: true`) get `{"status": "error", "detail": "<same message, no glyph>"}` with the same status code (D-04).

### Lifetime

| Event | Slot result |
|---|---|
| Any error response from any htmx request (scan, flip continue/abort, tag/correspondent refresh, tags/correspondents load, history load, status poll) | children replaced with the error partial; a newer error replaces an older one |
| Status poll success (`GET /api/jobs/current/status`) | **unchanged**: the poll response must not contain `status-message` |
| Flip continue/abort success | **unchanged** |
| Tags, correspondents, cache-invalidate, history success | **unchanged** |
| **`POST /api/scan` success** | **emptied** by `<div id="status-message" hx-swap-oob="innerHTML"></div>` in the response (D-03). Empty OOB element, so the slot ends with zero children and zero height |
| Full page load / reload | empty |

### The one CSS rule this phase adds (`app.css`)

Placed directly after the `#status-area` rule:

```css
/* A request error sits just above the status area. Inset its text by the
   status area's own left border and padding so the two lines start at the
   same x. The border is transparent: the error colour stays text-only. */
#status-message > p {
    padding-left: 1rem;
    border-left: var(--pico-border-width) solid transparent;
}
```

- No margin override. Pico's `p { margin: 0 0 1rem }` supplies the 16 px gap to `#status-area`, and that margin collapses with `#status-area`'s `margin-top: 1rem`. The gap above the message is the Scan `article`'s existing `margin-bottom: 1rem`. Every vertical gap around the slot is therefore the existing 16 px.
- The comment explains the reason in plain words and cites no planning artefact (SWP-07 convention).
- No `!important`. No colour literal. No new class.

## S3 — Error Copy

All strings are developer-authored constants owned by `vocabulary.py`, following the "templates own no vocabulary" pattern: an enum with a total `match` + `assert_never` label function (research suggests a `RequestRejection`-style enum). The renderer passes the constant in; templates and routes never compose error prose.

**Style (inherited copy guide, applied):** sentence case; no exclamation marks; no emoji; each slot message states **the problem, then what to do next**; slot messages end with a period (they are full sentences, like `vocabulary.error_message`). Job-row `error` texts have **no trailing period**, matching the existing `job.error` convention (`"Manual duplex scan aborted at the flip prompt"`).

### Slot messages (HTML branch renders `✗ ` + message; JSON `detail` is the message alone)

| Case | Status | Message (verbatim) |
|---|---|---|
| Queue full (ROBU-02) | 429 | `The scan queue is full. Wait for a scan to finish, then try again.` |
| Worker thread down (D-05, D-11) | 503 | `The scan service is not running, so the scan was not started. Restart saneless, then try again.` |
| Worker degraded: job store failing (D-10, D-11) | 503 | `Job history cannot be saved right now, so the scan was not started. Check the server's free disk space and log, then try again.` |
| Unknown profile (ROBU-08) | 422 | `That scan profile does not exist. Reload the page to see the current profiles.` |
| Title too long (ROBU-08) | 422 | `The title is too long. Shorten it to 256 characters or fewer.` |
| Any other request validation failure (bad `resource`, malformed or missing form field such as `job_id`, non-integer tag) | 422 | `The request was not valid. Reload the page, then try again.` |
| Cross-site request blocked (D-22) | 403 | `This request was blocked because it did not come from the saneless page. If saneless is behind a reverse proxy, make sure the proxy passes the original Host header.` |
| Not found (router 404, `StaticFiles` 404) | 404 | `That page or action does not exist. Reload the page, then try again.` |
| Method not allowed | 405 | `That action is not allowed. Reload the page, then try again.` |
| Unhandled exception (catch-all) | 500 | `Something went wrong on the server. Check the server log for details, then try again.` |
| Any other 4xx not listed (totality) | as raised | `The request could not be completed. Reload the page, then try again.` |
| Any other 5xx not listed (totality) | as raised | same as the 500 message |

Notes binding on the implementation:
- **`256`** is the ROBU-08 cap the review suggests (`Form(max_length=256)`). The number in the copy and the `maxlength` attribute (S5) come from the same constant. If the planner picks a different cap, all three change together.
- **Title-too-long vs other 422s** is decided from the validation error's location (`body` → `title`) and type (string too long). The handler never reads, logs or renders the error's `input` value; it holds the raw oversized title.
- **Precedence:** FastAPI validates the form before the handler body runs. A request with both an over-long title and an unknown profile therefore gets the title message. That is acceptable and needs no special case.
- **403 wording targets the only person who can see it.** A genuinely cross-site page never displays saneless's response. The user who reads this message is on the saneless page behind a misconfigured proxy (or behind `Referrer-Policy: no-referrer`, research Pitfall 8), so the next step names the proxy.
- **The 500 message never includes exception text.** Details go to the server log only (`exc_info`).

### Job-row `error` texts (written to the store; rendered by `saneless jobs` and, for the restart case, by the status area)

| Case | `error` text (verbatim) | Where the user sees it |
|---|---|---|
| Submit rejected: queue full (D-05) | `Not started: the scan queue was full` | History Status cell `Failed` (`.status-error`); CLI job listing. **Never** the status area (D-06) |
| Submit rejected: worker down (D-05) | `Not started: the scan service was not running` | same |
| Submit rejected: worker degraded, row write succeeded (D-05, D-11) | `Not started: the scan service was unavailable` | same |
| Crash recovery (`fail_active_jobs` reason, D-13; also a flip wait aborted by shutdown, research Open Question 2) | `The server restarted before this scan finished` | Status area on the next page load when it is the most recent run job: `✗ Error: The server restarted before this scan finished` (`role="alert"`, `.status-error`, existing ERROR branch); History `Failed` |

The history table's visual presentation of these rows is unchanged: humanised label `Failed`, class `.status-error`. There is no new history column and no "Rejected" label.

## S4 — Server-Owned Scan Button (ROBU-04)

### One source of markup

`partials/scan_button.html` is the **only** place the button markup exists:

```html
<button type="submit" id="scan-btn"{% if oob %} hx-swap-oob="true"{% endif %}
        {% if job and job.is_active %}disabled{% if job.is_busy %} aria-busy="true"{% endif %}{% endif %}>
    {% if job and job.state == JobState.AWAITING_FLIP %}Waiting for flip&#8230;{% elif job and job.is_busy %}Scanning&#8230;{% else %}Scan{% endif %}
</button>
```

- `type="submit" id="scan-btn"` stay the **first two attributes, in that order** (`tests/test_web_state_rendering.py::_SCAN_BUTTON` depends on it).
- `index.html` includes it inside the form with `oob` unset.
- `partials/status_response.html` includes `partials/status.html`, then the button with `oob = true`, then, only when `clear_message` is set, the S2 OOB clear element.
- **Never** put the OOB button inside `partials/status.html`. `index.html` includes that partial, so the full page would carry two `id="scan-btn"`.

### State table (rule carried forward unchanged; who renders it is what changes)

| Job (current, else most recent run job) | `disabled` | `aria-busy` | Label (source text) | Rendered label |
|---|---|---|---|---|
| none (idle) | absent | **absent** | `Scan` | Scan |
| `PENDING` | present | `"true"` | `Scanning&#8230;` | Scanning… |
| `SCANNING` | present | `"true"` | `Scanning&#8230;` | Scanning… |
| `AWAITING_FLIP` (answered or not) | present | **absent** | `Waiting for flip&#8230;` | Waiting for flip… |
| `SCANNING_REVERSE` | present | `"true"` | `Scanning&#8230;` | Scanning… |
| `ASSEMBLING` | present | `"true"` | `Scanning&#8230;` | Scanning… |
| `UPLOADING` | present | `"true"` | `Scanning&#8230;` | Scanning… |
| `DONE` / `FALLBACK` / `ERROR` | absent | **absent** | `Scan` | Scan |

- `aria-busy` is **omitted**, never `"false"`, when not busy. The deleted `app.js` wrote `aria-busy="false"`; the test that asserts it is rewritten.
- The button's label uses the `&#8230;` entity (U+2026). This **resolves master-spec copy inconsistency #2** (`Scanning...` in Jinja vs `Scanning…` in JS): only the entity form remains. The status area's progress prose keeps its three ASCII periods; that is a different string with a different owner.
- `SCANNING_REVERSE` gets no label of its own. It is busy, so it reads `Scanning…`, exactly as it does in `index.html` today.

### Which responses carry what

| Response | `#status-area` | OOB `#scan-btn` | OOB clear `#status-message` |
|---|---|---|---|
| `GET /` (full page) | inline | **inline, not OOB** (exactly one) | n/a (slot rendered empty) |
| `POST /api/scan` success | yes | yes | **yes** |
| `GET /api/jobs/current/status` | yes | yes | **no** |
| `POST /api/flip/continue`, `POST /api/flip/abort` success | yes | yes | **no** |
| Any error response (S2) | no | **no** | no |
| Tags / correspondents / cache invalidate / history | no | no | no |

### Form wiring

```html
<form hx-post="/api/scan"
      hx-target="#status-area"
      hx-swap="outerHTML"
      hx-disabled-elt="#scan-btn"
      hx-disinherit="hx-disabled-elt">
```

- `hx-disabled-elt="#scan-btn"` replaces `app.js`'s `beforeRequest` handler. It prevents a double submit during the round-trip.
- `hx-disinherit="hx-disabled-elt"` is **mandatory**. Without it, the tags and correspondents `<select>`s (`hx-trigger="load"`) and both refresh buttons inherit `hx-disabled-elt`. On htmx 2.0.8, finishing those requests strips `disabled` from a button the server rendered disabled, so the Scan button would come back enabled on page load during an active job. That is C-10 reintroduced.
- No `hx-on`, no inline script, no `hx-indicator` is added.

### Interaction timeline (records one intended behaviour change)

| Moment | Button | Status area | Slot |
|---|---|---|---|
| Click (request in flight) | disabled by htmx; **label still `Scan`** | unchanged | unchanged |
| 200 from `POST /api/scan` | replaced OOB: disabled, `aria-busy="true"`, `Scanning…` | `Starting scan...` + 1 s poll | emptied |
| Each poll while active | replaced OOB per state table | per state | unchanged |
| Terminal poll | replaced OOB: enabled, `Scan`, no `aria-busy` | terminal line; poll stops; history reloads | unchanged |
| 4xx/5xx from `POST /api/scan` | htmx removes the `disabled` it added, so the button returns to its pre-click (enabled) state | unchanged | error message |

**Behaviour change, accepted:** the busy label now appears one round-trip after the click (when the OOB copy lands) rather than instantly, as `app.js` did. The button is disabled immediately, so there is no double-submit window. This is the price of a single source of truth (C-10).

**Known limit, accepted and out of scope:** a 429/503 on a page that loaded idle does not start the status poll. The slot says what happened. Queue position is APPL-08 (Phase 30).

## Accessibility Contract

| Concern | Contract |
|---|---|
| Alert region | `#status-message` carries `role="alert"` (implicit `aria-live="assertive"`, `aria-atomic="true"`) and is **present and empty in the initial HTML**, so a later insertion is announced reliably. It is not created dynamically |
| Single announcement | Error content has **no nested `role="alert"`** (`#status-message [role="alert"]` count is 0). The status area's own `✗ Error:` line keeps its `role="alert"`. It is a separate region with different content, so the two never announce the same text |
| Clearing | The OOB clear removes children only; removals are not announced. The empty region announces nothing |
| Repeat errors | A second identical error replaces the `<p>` node, so it may be announced again. That is intended: the user acted again and failed again |
| Focus | Nothing moves focus. The slot has no `tabindex`, and no `autofocus`, `focus()` call, `hx-on` handler or `show:`/`focus-scroll` swap modifier is added. After an error lands, `document.activeElement` is not the slot or inside it |
| Keyboard | Unchanged native behaviour. Enter in `#title-input` submits the form, and Tab reaches `#scan-btn` whenever it is enabled. A disabled `#scan-btn` is skipped natively. No key handlers are added |
| Busy semantics | `aria-busy="true"` on `#scan-btn` exactly for `BUSY_STATES` (S4 table); omitted otherwise |
| Contrast | The slot text uses `.status-error` on the page surface (the slot sits outside any `article`), so the 23.1 measurements apply unchanged: **7.83:1 light, 5.89:1 dark** (AA pass). No new colour, so no new measurement row |
| Glyph | `✗` is read as text, exactly like the existing status-area error line. The pattern is kept consistent rather than diverging with `aria-hidden` in one place only |
| Offline | The UI must be fully usable with no internet (ROBU-09). Nothing, fonts included, is fetched from a third-party origin |

**Accepted edge (not asserted):** if the status poll itself returns 5xx on every tick (a persistent server fault), the slot is re-rendered every second and a screen reader may repeat the 500 message. A permanently failing poll is a server fault that should be loud. Suppressing it would need client JavaScript, which this phase deletes.
