<objective>
Close CR-01, the phase's blocking gap: a job whose terminal write and the guard's best-effort ERROR
write both failed must still reach ERROR once the store heals, even when the worker never became
degraded.

Purpose: `ScanWorker._idle_housekeeping` (src/saneless/worker.py ~757-777) calls `_try_recover` (the
only code that drains `_unrecorded_failures`) only while `self._degraded.is_set()`. One loop-level
failure counts 1 of `_DEGRADED_AFTER = 3`, and the next successful job resets the count, so the row
stays PENDING/SCANNING forever. `#status-area` polls it, `scan_button.html` renders `disabled`
(`job.is_active`), and `/health` stays 200. This breaks ROBU-01 success criterion 1 ("with the
browser reflecting reality afterward") and D-12's "recovery needs no user scan".
`tests/test_worker.py::test_a_failed_best_effort_write_is_only_logged` currently asserts
`stranded.is_active` and so locks the bug in. It must be corrected, not just supplemented.

Fix, per 26-REVIEW.md CR-01: retry owed writes on every idle tick whenever any are owed. The probe and
the degraded clear stay in the degraded path only.

Output: a shared `_flush_unrecorded_failures` helper, a corrected test and new worker and web tests
that fail today for the real reason, and the architecture doc sentence updated to match.

Out of scope: WR-01 rejected-submit rows (26-16, 26-17), and WR-02..WR-09 and IN-01..IN-05. Do not
change WR-02's success-write classification or IN-03's sleep-based "nothing happened" tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker thread -> SQLite job store | transient I/O errors (`database is locked`, disk full) surface as exceptions on writes |
| job store -> browser (status poll, Scan button) | a stale active row is rendered as a live job and disables scanning |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-60 | Denial of service | `_idle_housekeeping` leaving an unrecorded failure un-retried below `_DEGRADED_AFTER` (CR-01): Scan button disabled until restart | mitigate | `_flush_unrecorded_failures()` runs on every idle tick when not degraded; parametrized worker test (1 and 2 stranded) plus web test asserting `#scan-btn` re-enables |
| T-26-61 | Denial of service | a retry loop that degrades a worker over a single unwritable row | mitigate | failed retries log DEBUG and are not counted; test asserts `_consecutive_loop_failures == stranded` and HEALTHY after several failed retries |
| T-26-62 | Tampering (integrity) | a retried write overwriting a row that is actually running | mitigate | the flush runs only on a `queue.Empty` tick (no current job), and owed ids come only from `_best_effort_fail` for jobs the loop already abandoned; documented in the helper docstring |
| T-26-63 | Repudiation | a row silently changing state long after its job ended | mitigate | INFO log per owed row written, carrying the job id |
| T-26-SC | Tampering | package installs | accept | no new dependencies in this plan |
