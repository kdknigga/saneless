{# The status strip's swap target, and two load-bearing facts about it. 1. The poll trigger is emitted ONLY while the poll is wanted, and `poll_attempt` is the server saying so. The route sets it to the number the next request should carry, or to none when there is to be no next request -- and there are now two ways for that to happen. Nothing left in flight is the first and still the primary one: the body that replaces this one has the answer, carries no trigger, and so ends the poll. Running out of attempts is the second, and it exists because the first one cannot fire at all on an appliance whose refresher thread has died -- before it, an abandoned tab asked forever. There are two attempt bounds and the route picks between them: checks.POLL_ATTEMPT_CAP with nothing in flight, and the larger checks.POLL_PROBE_ATTEMPT_CAP while a probe demonstrably holds the refresher's single-flight lock, because the probe's own worst case is minutes and a chain that ended first never collected it. That is the in-tree idiom (partials/status.html lines 1-6) and it is deliberately NOT HTTP 286, which would need a change to the tuned htmx-config meta in base.html. 2. The strip asks only while something in flight will change the answer, and never otherwise. There are two such things, and the route (`_checks_context`) is where both are read. A cold cache is the first: no results yet, so a probe is coming. A probe holding the refresher's single-flight lock is the second: results exist, but this render is of the pre-probe entry and the probe's own `store` is seconds away, so without the ask nothing on the page would ever collect it and Check again could visibly do nothing. Once both are false the strip is refetched only by Check again, by the terminal-state reload, or by a page load. Every chain of asks is bounded by one of the two caps above whichever condition started it, so neither one is a steady-state poll: a permanent poll would keep the lazy refresher awake for every abandoned browser tab, which is the exact cost its laziness exists to avoid. The attributes stay INSIDE the conditional. This is an outerHTML swap target, so an unconditional htmx request attribute here is a body that re-arms itself and a loop nothing can end. `load` rides only on the first body of a chain -- the one a page render or an out-of-band swap put here, which is the one `poll_attempt == 1` identifies. htmx re-fires `load` for content it has just swapped in, and this body swaps in a copy of itself, so a polled body carrying `load` requests again the instant it arrives: measured in Chromium at 42 requests a second against the 0.5 this markup advertises. The interval in the markup should be the interval the browser actually uses, and now it is. `oob` follows partials/scan_button.html: the one copy of this markup renders itself out-of-band when a scan submit carries it, so the swap target's id is never duplicated by a wrapper around a second copy of this markup. The template owns no vocabulary. Every class, glyph and word comes either from a Jinja filter implemented in saneless.checks or from a constant this route already put on the row -- the give-up line included, which arrives as `freshness_line` -- and the only conditions here are "are there results yet" and "did the server ask for another attempt", never a comparison against a CheckState value. The filters the results branch reaches for take the WHOLE result rather than its state, because the state is not on its own enough to draw the row: a result the registry skipped carries CheckState.OK so that `saneless doctor` keeps exiting 0 for a probe nobody took, and drawing from that state put a green tick in front of "Not checked while a scan is running." Choosing the marker from the result, `skipped` flag included, is a Python decision in check_row_class / check_row_glyph / check_row_label -- which is what keeps the rule out of here and keeps `doctor` reading the same flag through cli._row_marker. #} {# `state_class`, `glyph` and `state_label` are what THIS ROW renders, not what its state renders.
